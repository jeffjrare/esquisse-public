# Landing and SEO: found, shared, fast

**As of:** 2026-10-28

**Paths:** `*.astro`, `astro.config.*`, `landing/`, `marketing/`, `robots.*`, `sitemap*`, `*Seo*`, `*seo*`

**Stack:** `astro`, `@astrojs/*`, `next-sitemap`

**If today is more than 180 days past `**As of:**`, say so in one line before relying on a threshold or a generator's option, and keep going.** Re-check a dated fact against its source before it decides anything.

**A project skill on the same topic wins** where the two disagree. Self-hosted fonts and the font stack belong to `esq:design-system`; headings, landmarks, alt text and `lang` to `esq:accessibility`; the French and English copy itself, and which language a visitor reads, to `esq:i18n-fr-en`; a Content-Security-Policy on the site to `esq:web-security`. This module owns what a crawler and a link preview read from a public page, and how fast that page becomes usable.

An SEO mistake throws no error: the page renders, the deploy is green, and the site is simply absent from results, indexed under its staging host, or shared as a bare link. It shows weeks later in Search Console, if anyone looks. Each rule below says how to see it the day it ships.

**These rules are documented, not yet tested in a shipped project.** They follow web.dev, Google Search Central, the Open Graph protocol and the Astro documentation, checked on the date above, and state the general rule first; Astro specifics are conditional. Treat each as a hypothesis to prove on the first page that relies on it.

## Fast on a real phone

- **Core Web Vitals are judged from field data at the 75th percentile, with INP for responsiveness.** *Why:* the "good" thresholds are LCP ≤ 2.5 s, INP ≤ 200 ms and CLS ≤ 0.1, measured at the 75th percentile of page loads, mobile and desktop apart; INP replaced FID as a stable Core Web Vital in 2024 ([Web Vitals](https://web.dev/articles/vitals), checked 2026-10-28). A lab run on a fast laptop passes pages that real phones fail, and a lab tool cannot measure INP at all, since it needs a real interaction. *Fix:* ship less JavaScript on the landing page (no client framework for static copy), defer third-party scripts (chat widgets, tag managers) until after load or interaction, and keep event handlers short. *Check:* the Search Console Core Web Vitals report or the CrUX data in PageSpeed Insights for the live URL, read for mobile; a lab score is a hint, never the verdict.
- **Every image reserves its space, and the hero image is not lazy.** *Why:* an image without `width` and `height` (or an `aspect-ratio`) pushes the text down when it arrives, which is CLS; a lazy-loaded hero image is fetched last and becomes a slow LCP. *Fix:* give each `<img>` its intrinsic dimensions, serve responsive sizes (`srcset`, `sizes`) in a modern format, `loading="lazy"` only below the fold, and `fetchpriority="high"` on the one LCP image. *Fix, conditional on Astro:* `<Image />` infers dimensions for an image imported from `src/` and processes it; a file in `public/` is copied as-is, unoptimised ([images](https://docs.astro.build/en/guides/images/), checked 2026-10-28), so the hero belongs in `src/`, and the component's lazy default is overridden for it. *Check:* load the page throttled in DevTools with the Performance panel's layout-shift track, and see no shift after first paint.

## What a search result shows

- **Each page has its own `<title>`, meta description and a self-referencing absolute canonical in `<head>`.** *Why:* a shared title across pages makes them look like duplicates; `rel="canonical"` is a strong signal, not a directive, it is accepted only in `<head>`, and a relative canonical breaks when the page is served from another host or path ([canonicalization](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls), checked 2026-10-28). A canonical copied from a template that points every page at the home page removes them all from results. *Fix:* build title, description and canonical from the page's own data in one layout component, the canonical from the production origin (never `localhost` or the staging host), and never use `noindex` or `robots.txt` to choose a canonical. *Check:* view the built HTML of three pages; each canonical is absolute, on the production host, and names that page.

## What a shared link shows

- **Open Graph's four required tags are present, with an absolute image URL sized for a large card.** *Why:* `og:title`, `og:type`, `og:image` and `og:url` are the required properties ([Open Graph protocol](https://ogp.me/), checked 2026-10-28); without an image the link shares as bare text. Facebook asks for at least 1200 × 630 px at about 1.91:1 for the best display, 8 MB at most, and caches the image by URL, so a replaced image needs a new URL ([sharing images](https://developers.facebook.com/docs/sharing/webmasters/images/), checked 2026-10-28). *Fix:* one card image per page or a sensible default, 1200 × 630, its URL absolute and versioned (`og-home.v2.png`), with `og:image:width` and `og:image:height`; add `twitter:card` set to `summary_large_image` for X. X's card documentation refused automated reads on the date above (402): confirm there which `og:` tags X falls back to before relying on the fallback. *Check:* paste the production URL into a platform's sharing debugger and into a chat app, and see the image, title and description.

## What a crawler may see

- **Staging is kept out of the index by a header or a password, never by `robots.txt` alone.** *Why:* a `Disallow` does not keep a page out of Google's index, and a URL linked from elsewhere can still appear; a page blocked by `robots.txt` is never crawled, so its `noindex` is never seen ([robots.txt](https://developers.google.com/search/docs/crawling-indexing/robots/intro), [noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing), checked 2026-10-28). The common failure runs both ways: staging indexed under its own host, or a `noindex` left from staging shipped to production. *Fix:* staging answers every response with `X-Robots-Tag: noindex` (or sits behind basic auth), set by the environment, never by a file that gets deployed to production; production sends neither. *Check:* `curl -sI https://staging…/ | grep -i x-robots-tag` shows `noindex`; the same on production shows nothing, and production's HTML carries no `noindex` meta tag.
- **The sitemap lists only canonical, absolute, indexable URLs, and `robots.txt` points to it.** *Why:* Google crawls sitemap URLs exactly as listed, ignores `<priority>` and `<changefreq>`, trusts `<lastmod>` only when it is consistently accurate, and caps each file at 50 000 URLs or 50 MB uncompressed ([build a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap), checked 2026-10-28). A sitemap listing redirected, `noindex` or staging URLs teaches the crawler to distrust it. *Fix:* generate it at build time from the routes, with a `lastmod` from the content's real change date or none at all, and a `Sitemap:` line with its absolute URL in `robots.txt`. *Fix, conditional on Astro:* `@astrojs/sitemap` needs the `site` option (starting with `http://` or `https://`), writes `sitemap-index.xml` with numbered files, includes `getStaticPaths()` routes but not on-demand rendered ones ([sitemap integration](https://docs.astro.build/en/guides/integrations-guide/sitemap/), checked 2026-10-28), so an SSR page needs its own entry. *Check:* fetch the built sitemap, request every URL it lists, and see each answer 200 with a canonical equal to itself.

## French and English pages that point to each other

- **Each language version lists itself and every other version, with `x-default`.** *Why:* annotations that are not reciprocal are ignored; each version must list itself as well as the others; codes are ISO 639-1 with an optional ISO 3166-1 region (`fr-CA`, `en-CA`), a country alone is invalid, and URLs are fully qualified ([localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions), checked 2026-10-28). A French page that links to the English one with no link back leaves Google to guess which one a Québec searcher sees. *Fix:* one of the three equivalent methods (HTML `<link rel="alternate" hreflang>`, the HTTP `Link` header, or the sitemap), the same set on every version, `x-default` on the language chooser or the default; each alternate URL is the canonical of its version. *Fix, conditional on Astro:* `@astrojs/sitemap`'s `i18n` option (`defaultLocale`, `locales`) writes the alternates into the sitemap. *Check:* for one page pair, read both pages' alternates (or both sitemap entries) and see the same complete, reciprocal set.

## Structured data that matches the page

- **Structured data is JSON-LD and describes only what the page shows.** *Why:* Google recommends JSON-LD, warns against markup about information not visible to the user, and a valid markup still does not guarantee a rich result ([structured data](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data), checked 2026-10-28). An `Organization`, `Product` or `FAQPage` block copied from a template with a stale price or a question the page no longer shows is a policy issue, not a bonus. *Fix:* generate the JSON-LD from the same data the page renders, with every required property of its type. *Check:* Google's Rich Results Test on the production URL reports the type valid with no missing required property.
