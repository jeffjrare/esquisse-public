# Deploying to a VPS: the deploy nobody notices

**As of:** 2026-10-28

**Paths:** `ansible/`, `deploy/`, `infra/`, `nginx/`, `*nginx*`, `ecosystem.config.*`, `playbook*`

**Stack:** `pm2`

**If today is more than 180 days past `**As of:**`, say so in one line before relying on a tool's default or Cloudflare's IP list, and keep going.** Re-check a dated fact against its source before it decides anything.

**A project skill on the same topic wins** where the two disagree. How a queue worker finishes its jobs on shutdown belongs to `esq:background-jobs`; the database pool across pm2 instances and `migrate deploy` to `esq:prisma-postgres`; rate limits keyed on the client IP this module restores, and secrets in logs, to `esq:web-security`; the health endpoint and uptime check themselves to `esq:observability`. This module owns how a release reaches the server, how the server sits behind nginx and Cloudflare, and how a restart drops nothing.

A deploy bug never shows on a quiet server: the reload takes a second and nobody was mid-request. It shows as a 502 burst on every release, rate limits that ban Cloudflare instead of a visitor, or an origin anyone can reach around the CDN. Each rule below says how to see it first.

**These rules are documented, not yet tested in a shipped project.** They follow the pm2, nginx, Cloudflare and Ansible documentation, checked on the date above, and state the general rule first; pm2, systemd and Cloudflare specifics are conditional. Treat each as a hypothesis to prove on the first deploy that relies on it.

## Restarts that drop no request

- **A restart replaces processes one at a time and only after the new one listens.** *Why:* a plain restart kills every process and starts them again; requests arriving in between get a 502 from nginx. Conditional on pm2, `reload` in cluster mode restarts instances one by one for zero downtime, where `restart` kills and restarts, and a reload that does not complete in time falls back to a classic restart ([cluster mode](https://pm2.keymetrics.io/docs/usage/cluster-mode/), checked 2026-10-28). *Fix, conditional on pm2:* `exec_mode: 'cluster'` with at least two instances, `wait_ready: true` and `process.send('ready')` once the server listens (and its database and cache connections are up), `listen_timeout` longer than a cold start (pm2 waits 3000 ms by default) ([graceful start and shutdown](https://pm2.keymetrics.io/docs/usage/signals-clean-restart/), checked 2026-10-28). *Fix, conditional on systemd:* one unit cannot hand over to its replacement; run two instances behind nginx and restart them in turn, or use socket activation so the listening socket outlives the process. *Check:* run a load loop (`while true; do curl -s -o /dev/null -w '%{http_code}\n' https://…/health; done`) across a deploy and count anything but 200.
- **The app closes its server on the signal it is sent, within the manager's timeout.** *Why:* pm2 sends `SIGINT` (configurable by `PM2_KILL_SIGNAL`), then `SIGKILL` if the process has not exited, after 1.6 s unless `kill_timeout` says otherwise; systemd sends `SIGTERM`. An app with no handler dies with its open requests. *Fix:* on both `SIGINT` and `SIGTERM`, stop accepting (`server.close()`), let in-flight requests finish, close pools, then exit; set `kill_timeout` (or systemd's `TimeoutStopSec`) above the slowest normal request. Workers finishing jobs are `esq:background-jobs`'s. *Check:* start a request that sleeps five seconds, reload, and see it complete.
- **A long-lived connection (WebSocket, SSE) is expected to drop on a deploy.** *Why:* `server.close()` waits for it forever, so the old process lingers until `SIGKILL`. *Fix:* close those connections deliberately on the signal and make the client reconnect with backoff.

## nginx in front of the app

- **The app knows it is behind exactly one proxy, and trusts only that hop.** *Why:* behind nginx the socket address is `127.0.0.1`; without `X-Forwarded-For` and `X-Forwarded-Proto` the app logs one IP for everyone, builds `http://` redirect URLs and refuses `Secure` cookies; trusting the header from any hop lets a client forge its IP. *Fix:* nginx sets `proxy_set_header Host $host`, `X-Forwarded-For $proxy_add_x_forwarded_for`, `X-Forwarded-Proto $scheme`; the app trusts one hop (Express: `app.set('trust proxy', 1)`, or the loopback address). Rate limits on that IP are `esq:web-security`'s. *Check:* log `req.ip` and `req.protocol` from a production request; they show the visitor's address and `https`.
- **Upstream keepalive, body size and timeouts are set, not defaulted.** *Why:* without keepalive nginx opens a new connection to the app per request; `client_max_body_size` defaults to 1 MB, so an upload fails with 413 that the app never sees; `proxy_read_timeout` defaults to 60 s and cuts a long export or an SSE stream. *Fix:* an `upstream` block with `keepalive`, clearing the `Connection` header (`proxy_set_header Connection ""`) and, before nginx 1.29.7, `proxy_http_version 1.1`, which became the default there ([upstream module](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive), checked 2026-10-28); a body size matching the largest upload the app accepts; longer timeouts only on the routes that need them. *Check:* `nginx -T` shows each setting; upload a file just under the app's limit through nginx.

## Cloudflare in front of nginx

- **SSL mode is Full (strict), with a valid certificate on the origin.** *Why:* Flexible sends traffic from Cloudflare to the origin in clear, and Full accepts any certificate, so neither proves the origin. Full (strict) requires an unexpired certificate whose CN or SAN matches the hostname, issued by a public CA or by Cloudflare's Origin CA ([Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/), checked 2026-10-28). An app redirecting HTTP to HTTPS behind Flexible loops forever. *Check:* the zone's SSL/TLS setting reads Full (strict), and `openssl s_client -connect <origin-ip>:443 -servername <host>` shows the certificate.
- **nginx restores the visitor's IP from `CF-Connecting-IP`, and only for Cloudflare's addresses.** *Why:* behind Cloudflare every request comes from a Cloudflare address, so logs, rate limits and bans all see Cloudflare. *Fix:* `ngx_http_realip_module`: one `set_real_ip_from` per range in [Cloudflare's published list](https://www.cloudflare.com/ips/), and `real_ip_header CF-Connecting-IP` ([restoring visitor IPs](https://developers.cloudflare.com/support/troubleshooting/restoring-visitor-ips/restoring-original-visitor-ips/), checked 2026-10-28). Cloudflare says the list must be updated regularly: generate it from the published files in the playbook, never paste it once. *Check:* the access log shows visitors' addresses, not `172.64.*` or `104.16.*`.
- **The origin accepts web traffic only from Cloudflare.** *Why:* an origin reachable on its own IP bypasses the WAF, the cache and the rate limits, and the IP leaks through DNS history and certificate logs. *Fix:* the firewall (ufw, the host's security group) allows 80 and 443 only from the same published ranges, or a Cloudflare Tunnel with no inbound port at all; SSH stays restricted separately. *Check:* `curl -k https://<origin-ip>/` from outside times out.
- **No cache rule caches an authenticated response.** *Why:* a "cache everything" rule serves one user's page, with their name or data, to the next visitor. *Fix:* cache only static assets by path or extension, send `Cache-Control: private, no-store` on every authenticated response, and bypass the cache when a session cookie is present. *Check:* request a signed-in page twice from two browsers and read `cf-cache-status`; it is never `HIT`.

## Ansible runs twice without changing anything

- **A playbook is idempotent: a second run reports no change.** *Why:* a `shell` task that appends a line or restarts the app on every run makes each deploy a different deploy, and a failed run cannot simply be run again. *Fix:* modules over `shell` (`lineinfile`, `template`, `systemd`), `creates:` or `changed_when:` on the commands that remain, and restarts through handlers notified only by a change. *Check:* run the playbook twice against staging; the second recap shows `changed=0`, deploy tasks aside.
- **Secrets live in Ansible Vault, and never print.** *Why:* a `.env` committed in a role or a variable echoed by a failing task is in the repository or the CI log. *Fix:* encrypt variable files or single variables with Ansible Vault ([Vault guide](https://docs.ansible.com/ansible/latest/vault_guide/index.html), checked 2026-10-28), keep the vault password out of the repository, and set `no_log: true` on tasks that template or pass a secret. *Check:* `git grep` the repository for each secret's first characters; the playbook output with `-v` shows none.

## Deploy order, and the way back

- **Build, migrate, reload, check, and roll back on failure, in that order.** *Why:* building on the server while the old release serves makes the box slow and leaves a half-built tree if it fails; reloading before migrating serves code against a schema it does not know. *Fix:* build in CI or into a new release directory (`releases/<sha>`), run migrations (expand-then-contract and `migrate deploy` are `esq:prisma-postgres`'s), switch a `current` symlink, reload, then call the health endpoint; on failure switch the symlink back and reload. Keep the last few releases. *Check:* deploy a release whose health check fails on purpose in staging and see the previous one serving again within the script's run.
