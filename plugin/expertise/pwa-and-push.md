# PWA and push: the app that stays current, the push that still arrives

**As of:** 2026-10-28

**Paths:** `sw.*`, `service-worker.*`, `*serviceWorker*`, `manifest.webmanifest`, `push/`, `push.*`, `*Push*`, `*webpush*`, `*web-push*`

**Stack:** `vite-plugin-pwa`, `workbox-window`, `workbox-build`, `serwist`, `@serwist/*`, `web-push`, `@capacitor/push-notifications`, `@capacitor-firebase/messaging`, `firebase-admin`

**If today is more than 180 days past `**As of:**`, say so in one line before relying on a browser's support or FCM's API, and keep going.** Re-check a dated fact against its source before it decides anything.

**A project skill on the same topic wins** where the two disagree. The native shell's push token, entitlement and Firebase setup belong to `esq:capacitor-ios` and `esq:capacitor-android`; what a notification may show on the lock screen to `esq:store-review`; sending from a queue, retries and idempotency to `esq:background-jobs`; the language of a notification to `esq:i18n-fr-en`. This module owns the service worker's lifecycle and caches, installability, the web push subscription, and the server's side of every push: keys, the send API and the token lifecycle.

Both failures are silent by construction. A service worker keeps serving last week's app from its cache after a deploy, and nobody on the team sees it because their tabs updated long ago. A push that stopped arriving sends nothing back: the user just stops coming. Each rule below says how to see it first.

**These rules are documented, not yet tested in a shipped project.** They follow MDN, web.dev, WebKit's announcement, RFC 8030, RFC 8292 and Firebase's documentation, checked on the date above, and state the general rule first; Workbox, vite-plugin-pwa and FCM specifics are conditional. Treat each as a hypothesis to prove on the first release that relies on it.

## The update lifecycle

- **A new service worker waits until no tab uses the old one, so a deploy is not an update.** *Why:* after a new worker installs it waits until the old one controls no client, and a reload is not enough because the old worker still controls the page during the navigation ([lifecycle](https://web.dev/articles/service-worker-lifecycle), checked 2026-10-28). An installed PWA that is never fully closed runs the old release for days, against an API that has moved on. *Fix:* detect the waiting worker and offer a reload (conditional on vite-plugin-pwa: `registerType: 'prompt'`, the default, with `onNeedRefresh` and `updateSW()` ([prompt for update](https://vite-pwa-org.netlify.app/guide/prompt-for-update.html), checked 2026-10-28); conditional on Workbox: `workbox-window`'s `waiting` event); keep the API tolerant of the previous client for at least one release. *Check:* open the installed app, deploy, return to it, and see the update offered within one navigation; leave it open across two deploys and see it still work.
- **`skipWaiting()` mid-session is chosen, not defaulted.** *Why:* it makes the new worker take over pages loaded by the old one, so one page's early fetches are served by the old worker and its later ones by the new, which breaks a lazy-loaded chunk whose hashed file the new cache no longer has ([lifecycle](https://web.dev/articles/service-worker-lifecycle), checked 2026-10-28). An automatic update that reloads the page also discards what the user was typing. *Fix:* call `skipWaiting()` only from the user's "reload" action, then reload; an automatic mode is for apps with no unsaved state. *Check:* with a form half-filled, deploy and see the prompt, never a forced reload.
- **The worker script itself is never cached into staleness, and its scope is where it lives.** *Why:* browsers fetch the registered script from the network on an update check by default, but `importScripts()` files still follow their caching headers, and `updateViaCache: 'all'` puts the main script back behind the HTTP cache; a worker's scope is its own directory unless the server sends `Service-Worker-Allowed` ([register](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register), checked 2026-10-28), so `/assets/sw.js` cannot control `/`. *Fix:* serve the worker from the root with `Cache-Control: no-cache`, keep the default `updateViaCache`, and version imported scripts by file name. *Check:* `curl -sI https://…/sw.js` shows `no-cache`; DevTools › Application shows the scope as `/`.

## What the cache may serve

- **HTML and authenticated API responses are network-first or never cached; only hashed assets are cache-first.** *Why:* cache-first HTML serves an old shell pointing to hashed bundles that the deploy deleted, a blank screen offline and online alike; a cached authenticated response survives logout and is served to the next account on a shared device. *Fix:* precache the hashed build assets the build generates (Workbox or Serwist manifest), network-first with a timeout and an offline page for navigations, no caching for `/api/` requests that carry a session, and clear the runtime caches on logout. *Check:* sign out, go offline and open a page that showed account data: it shows the offline page, not the data; after a deploy, no request for an old hash returns 404.

## Installable

- **The manifest meets the install criteria, and the app is served over HTTPS.** *Why:* Chrome promotes installation only with a manifest naming `name` or `short_name`, `icons` at 192 and 512 px, `start_url`, a `display` of `fullscreen`, `standalone`, `minimal-ui` or `window-controls-overlay`, and `prefer_related_applications` absent or `false`, plus some engagement ([install criteria](https://web.dev/articles/install-criteria), checked 2026-10-28). On iOS, only a manifest with `display` set to `standalone` or `fullscreen` makes a Home Screen web app rather than a bookmark, which web push depends on ([WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), checked 2026-10-28). *Check:* DevTools › Application › Manifest reports no installability error; on an iPhone, Add to Home Screen opens without Safari's address bar.

## Web push: keys, permission, subscription

- **Permission is asked from a user's tap, after saying what the notifications are for.** *Why:* iOS and iPadOS 16.4 brought web push to web apps added to the Home Screen only, and the request must come from a direct user interaction ([WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), checked 2026-10-28); a prompt on page load is refused there, and a "Block" answered anywhere is permanent unless the user digs into settings. *Fix:* an in-app explanation with a button that calls `Notification.requestPermission()`; on iOS outside a Home Screen install, show how to install instead of a dead button; the app works with push refused. *Check:* in Safari on an iPhone, the button explains installing; installed, the tap shows the system prompt.
- **One VAPID key pair per environment, its private half a server secret, and `userVisibleOnly: true`.** *Why:* VAPID signs each push with an ES256 JWT whose `exp` is at most 24 hours ahead, and a subscription made with a public key accepts only pushes signed by its private key (401 absent, 403 invalid) ([RFC 8292](https://datatracker.ietf.org/doc/html/rfc8292), checked 2026-10-28); rotating the key orphans every existing subscription. Chrome and Edge reject `subscribe()` unless `userVisibleOnly` is `true` ([subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe), checked 2026-10-28), so every push must show a notification. *Fix:* generate the pair once per environment, pass the public key as `applicationServerKey`, keep the private key in the server's secrets, and include the required `TTL` header on every send (a push service answers 400 without it, [RFC 8030 § 5.2](https://www.rfc-editor.org/rfc/rfc8030.html#section-5.2), checked 2026-10-28). *Check:* a push sent with staging's key to a production subscription is refused; a push from production arrives with the app closed.

## The server's token lifecycle

- **A subscription or token the push service reports gone is deleted, and the client re-sends its current one.** *Why:* a push service must answer 404 to a send to an expired subscription ([RFC 8030 § 7.3](https://www.rfc-editor.org/rfc/rfc8030.html#section-7.3), checked 2026-10-28), and push services also answer 410 for an endpoint the user unsubscribed; Safari does not promise either promptly. For FCM, `UNREGISTERED` (404) means the registration is invalid, as does `INVALID_ARGUMENT` (400) when the payload is known valid; FCM treats a registration as stale after a month without connecting, and on Android expires one inactive for 270 days, with no such expiry on iOS ([token management](https://firebase.google.com/docs/cloud-messaging/manage-tokens), checked 2026-10-28). A table that only grows sends to the dead, slows every fan-out and hides the live delivery rate. *Fix:* store each subscription or token with the user and a last-seen timestamp, delete it on those errors, prune ones older than your staleness window, and have the client send `getSubscription()` (or the native token) on each start and on `pushsubscriptionchange`. Firebase's page now recommends registering Firebase Installation IDs over legacy registration tokens where the SDK supports it: check the SDK in use before building on either. *Check:* revoke notification permission on a test device, send, and see the row deleted; the count of stored tokens per active user stays near one or two.
- **FCM is sent through the HTTP v1 API, authorised by a short-lived OAuth token from a service account.** *Why:* the legacy HTTP and XMPP APIs and their server keys were deprecated in June 2023 and shut down from July 2024 (Firebase's "Migrate from legacy FCM APIs to HTTP v1" guide, as a search quoted it on 2026-10-28; the page answered 404 to automated reads, so confirm the date there); v1 takes a Bearer token with the `https://www.googleapis.com/auth/firebase.messaging` scope, which the Admin SDK mints and refreshes itself ([authorize send requests](https://firebase.google.com/docs/cloud-messaging/auth-server), checked 2026-10-28). Code copied from an older tutorial posts to `fcm.googleapis.com/fcm/send` with a `key=` header and fails. *Fix, conditional on `firebase-admin`:* `messaging().send()` or `sendEach…` with the service account from the server's secrets; without it, a Google Auth Library token. Sending in bulk, retries and backoff are `esq:background-jobs`'s. *Check:* `git grep -n 'fcm/send\|key=AAAA'` finds nothing, and one test message reaches a device.
