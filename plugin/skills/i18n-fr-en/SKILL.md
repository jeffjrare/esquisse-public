# FR/EN localisation for Québec: both languages, every string

**As of:** 2026-10-25

**Paths:** `locales/`, `i18n/`, `i18n.*`, `messages/`, `*.po`, `fr.json`, `en.json`

**If today is more than 180 days past `**As of:**`, say so in one line before relying on a statute's wording or an engine's output, and keep going.**

**A project skill on the same topic wins** where the two disagree. `lang` on the document and on mixed-language passages belongs to `esq:accessibility`; sorting options by their translated label to `esq:forms-and-failures`; instants, zones, local days and DST to `esq:dates-and-timezones`. This skill owns which string the user reads and how a number, an amount or a date is written in their language.

A bilingual product breaks quietly: the missing string falls back to the other language, nothing throws, and the person who would notice is not the one testing. Each rule below says how to see it.

**One rule here is documented, not tested in a shipped project:** French's `many` plural category (below) is in CLDR and `Intl.PluralRules` returns it, but no shipped project here has a message that exercises it yet. Check it in the first count that can reach a million.

## Strings

- **Every user-facing string is a translation key, never a literal.** *Why:* a literal is a string one locale can never see, and no test fails on it. That includes text the server sends: an error or a validation message is a key resolved in the caller's language, so the client never shows a raw key or the server's default language. *Check:* grep the changed components and handlers for quoted prose outside the locale files; a lint rule (`eslint-plugin-i18next`'s `no-literal-string`, `eslint-plugin-formatjs`'s `no-literal-string-in-jsx`) catches the next one.
- **A key is added to both locales in the same commit, and a check fails the build on a gap.** *Why:* i18n libraries fall back silently (i18next to `fallbackLng`, `react-intl` to the default message), so a missing English key renders French on an English screen and nothing reports it. A key missing from an email template ships to an inbox, where it cannot be fixed afterwards. *Fix:* a script that compares the two locale trees and fails on a missing key, an empty value, mismatched interpolation placeholders (`{{name}}`, `{name}`) and a type mismatch (string vs array), run in CI ahead of the tests. *Check:* delete one English key locally and see the check fail.
- **Nest grouped keys by their token** (`range.options.day`, not `range_day`). *Why:* i18next reads `_` as its plural-suffix separator (`key_one`, `key_other`), so a flat key with an underscore collides with plural resolution the day someone adds a count. Conditional on i18next; other libraries have their own reserved suffixes.
- **Validation messages and accessible names are translated too, not only visible copy.** *Why:* a schema's default message (Zod, Yup, Valibot) and an `aria-label` written inline are English literals the parity check never sees; a French screen-reader user hears English, and a French form shows "Required". *Fix:* pass a key-resolving error map to the schema library, and route every `aria-label`, `title`, `alt` and `placeholder` through the same translation function. *Check:* switch to French, submit an empty form, and read the errors; inspect icon buttons' `aria-label`.
- **Proper nouns stay as they are**: the product's name, a person's or a place's name, a trademark. *Why:* a translatable brand name gets translated, and the product ends up answering to two names. Keep the name in one constant and put it inside translated sentences through interpolation.
- **Leave room for French running about 20–30 % longer than English.** *Why:* a button, a tab or a table header sized on the English label truncates or wraps in French ("Save" / « Enregistrer »). The ratio is a working estimate, not a standard. *Check:* view the changed screens in French at the narrowest supported width.

## Which language a message uses

- **The language comes from the user's choice, not from a default or the browser's header.** *Why:* a francophone on an English-language phone who picked French in the app still sends `Accept-Language: en`. The client sends the in-app choice on every request, and the server resolves keys against it. *Check:* set the browser to English, the app to French, trigger a server error, read it in French.
- **A background job, an email or a push reads the recipient's stored language.** *Why:* a job has no request to read a header from; a default locale sends French to an English user (or the reverse), and only in production. *Fix:* store the language on the user, and resolve every job message with a translator fixed to it (`i18next.getFixedT(user.language)`, or the library's equivalent). *Check:* a job test with one user of each language asserts each message's language.

## Québec French, numbers, money and dates

- **Québec French, not France French.** Courriel (not e-mail or mail), magasiner (not faire du shopping), clavarder (not chatter), fin de semaine (not week-end), téléverser (upload). *Why:* France-French terms read as foreign or as English to a Québec user; the [OQLF's Grand dictionnaire terminologique](https://vitrinelinguistique.oqlf.gouv.qc.ca/) is the reference for a term.
- **OQLF typography, which differs from France's.** Per the OQLF's [spacing table](https://vitrinelinguistique.oqlf.gouv.qc.ca/22039/la-typographie/espacement/espacement-avant-et-apres-les-signes-de-ponctuation-et-les-symboles) (checked 2026-10-25): a non-breaking space before `:`, `%` and `$`, and inside « guillemets »; **no space** before `;`, `!` and `?` (a thin space is acceptable where available). France puts a space before those three too. *Why:* without a non-breaking space, a line break lands between `25` and `%`, or before `:`. *Fix:* write U+00A0 (or U+202F) in the locale file, never a plain space. *Check:* search the French locale for ` :`, ` %`, ` $` followed or preceded by a plain U+0020.
- **Numbers, amounts and dates go through `Intl` with `fr-CA` or `en-CA`, never through string concatenation.** In `fr-CA`, `Intl.NumberFormat` writes `12 345,67 $` (space thousands separator, decimal comma, `$` after with a non-breaking space) and `25 %`; `en-CA` writes `$12,345.67`. *Why:* concatenating `'$' + amount.toFixed(2)` is correct in one language only. *Fix:* `new Intl.NumberFormat(locale, { style: 'currency', currency: 'CAD' })`, `Intl.DateTimeFormat(locale, { dateStyle: 'long' })` (« 8 mars 2026 »). The currency is the product's or the record's, never derived from the language: an English user in Québec still pays in CAD. *Check:* a test formats one amount and one date in each locale. Do not assert on the exact space character: Node 22's ICU uses U+00A0 as the thousands separator for `fr-CA` but U+202F for `fr-FR`, and ICU updates have changed this before; normalise spaces, or compare against the same `Intl` call.
- **Units are not translated; the currency is a fact of place.** *Why:* a kilogram is a kilogram in both languages; a hard-coded `$` in a template is true in Canada and false elsewhere. Store the currency with the amount when the product can leave the country.
- **Plurals go through ICU or the library's own rules, never `count === 1 ? a : b`.** *Why:* French treats 0 and 1 as singular (« 0 élément », "0 items"), English treats 0 as plural, and French has a `many` category for large round numbers (`Intl.PluralRules('fr-CA').select(1000000)` returns `many`: « 1 million **de** visiteurs »). *Fix:* ICU MessageFormat (`{count, plural, one {…} other {…}}`), or i18next's `_one` / `_other` / `_many` suffixes resolved by `Intl.PluralRules`. *Check:* render each pluralised message with 0, 1, 2 in both languages.

## The French-language obligation

**This states the rule and its source; whether and how it applies to a given product is the project's call, with its own counsel. It is not legal advice.**

- **Software offered in Québec must be available in French.** Charter of the French Language (CQLR c. C-11), [s. 52.1](https://www.legisquebec.gouv.qc.ca/en/document/cs/C-11) (consolidated text checked 2026-10-25): all computer software, including game software and operating systems, must be available in French unless no French version exists; it may also be available in other languages if the French version can be obtained on terms no less favourable (price aside, where it reflects higher costs) and has technical characteristics at least equivalent. Its history note shows it unchanged since 1997 (1997, c. 24, s. 3); the 2022 reform (Bill 96, S.Q. 2022, c. 14) did not amend it.
- **Documents around the product are covered too, and Bill 96 tightened them.** Same consolidation: s. 51 (inscriptions on a product and documents supplied with it, including directions for use and warranty certificates), s. 52 ("regardless of the medium used": catalogues, brochures, order forms and similar documents available to the public, which reaches a commercial website and its forms) and s. 57 (invoices and receipts) each carry a 2022, c. 14 amendment requiring that a version in another language not be available on more favourable terms than the French one. *Why it matters to code:* "French on terms at least as favourable" means a feature, a page or an email shipped in English first and French "later" is the failing case. *Check:* the parity check above, plus no route, feature flag or template that exists in one language only.
