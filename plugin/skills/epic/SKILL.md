Invocation input (may be empty): `$ARGUMENTS`. When present, `$0` is the first positional argument and `$1` the second.

You maintain `docs/epics/<slug>.md` — the home for an **epic**: a theme too large for one plan, worked across multiple plans over time. An epic sits one tier above a plan in esquisse's granularity: *task (one commit) < phase (one session) < plan (one initiative) < **epic (one theme, many plans)***. It is orthogonal to the backlog: the backlog is the capture bin; the epic is the narrative home that groups the plans and backlog items pursuing one outcome.

An epic doc has two kinds of content, and the split is the whole point:
- **Durable narrative** — `Goal`, `Scope`, `Status`, `Log`. Only a human writes these. You never invent them.
- **Generated views** — `## Plans` and `## Backlog`. You **rebuild these by scanning sources** every time you touch the epic, so they never drift. Never hand-maintain them as a wish-list.

The join key is the **epic slug** (e.g. `billing-overhaul`): it names the doc `docs/epics/<slug>.md`, fills the `Epic` column in `docs/BACKLOG.md` for tagged items, and appears as an `**Epic:** <slug>` line under the title of each plan belonging to the epic.

Do NOT use plan mode — it would block the file write. This command touches exactly one file: `docs/epics/<slug>.md` (plus creating `docs/epics/` if missing). It is **read-only against plans and the backlog** — it scans them but never edits them. Never change code, plans, or the backlog. Do not auto-run any other esq command.

**Pick the mode from the argument:**
- **No argument** → Mode B (list & status all epics).
- **First token is `new`** → Mode A (create). The rest is the title.
- **First token matches an existing epic slug** (`docs/epics/<slug>.md` exists — match leniently, ignore a `.md` suffix the user might type) → Mode C. If a change follows the slug → update it; if nothing follows → show & refresh that epic.
- **Any other text** → Mode A (create), deriving the slug from the text.

If `docs/epics/` does not exist, create it before writing (only when a mode actually writes a file).

---

## Mode A — Create (`new <title>`, or bare text)

The argument (minus a leading `new`) is the epic title.

### 1. Derive the slug
3–5 lowercase words from the title, hyphen-joined, descriptive of the theme (same convention as plan/brief slugs). If `docs/epics/<slug>.md` already exists, append `-2`, `-3`, … until unique — but first tell the user an epic with that slug exists and ask if they meant to open it instead (creating a near-duplicate epic is worse than reusing one). If they confirm it's genuinely new, proceed with the suffixed slug.

### 2. Write the epic doc
Create `docs/epics/<slug>.md` from the template at the end of this file. Fill `Title`, `Slug`, `Started` (today), `Status: Active`. Draft a one-line `Goal` and a first-pass `Scope` from the title and anything the user said — but keep them tight and mark them as a starting point the user should sharpen. Leave `## Plans` and `## Backlog` generated by an immediate scan (usually empty at creation — say so rather than inventing rows). Seed `## Log` with one line: `<today> — Epic opened.`

### 3. Commit and confirm
1. `git add docs/epics/<slug>.md && git commit -m "epic: open <slug>"`.
2. One-line confirmation: the path, the slug, and the two ways to attach work to it:
   - Tag backlog items: `/esq:backlog <text> epic:<slug>` (or `/esq:backlog B-3 B-5 B-9 epic:<slug>` to tag existing items — one ID, several, or a `B-3..B-7` range).
   - Tell `/esq:plan` this plan belongs to the epic (it records `**Epic:** <slug>` under the plan title); re-run `/esq:epic <slug>` afterward to pull it into the Plans view.

**Your conclusion is three zones, in this order, and nothing else.** The reader wants two facts — did it work, and does it need me — before any detail.

**1 · The headline.** One line, first, no preamble above it:

> `<glyph>  <command> — <your own counters> · <elapsed> · NEEDS YOU (<n>)`

`✔` nothing needs the user · `⚠` something does · `✖` you could not do your job. Drop `NEEDS YOU` when nothing does, and never soften the glyph: one open gate makes the whole run `⚠`.

**2 · What needs you.** Only what the user still has to settle — never a notice, and never work this command could do itself. One short ask per numbered line, action first, an executable one carrying its exact command in backticks. A genuine product choice takes the 🔴 option-set shape; a manual verification is copied verbatim with its starting state bracketed at the front. Absent whenever the headline is `✔`.

**3 · What happened.** One line per fact, never a sentence: glyph, label, value, evidence in its own column.

> ```
> ✔ fixed       6 items            a1b2c3d..e4f5a6b
> ○ still open  1 🟡               docs/plans/webhooks-fixes.brief.md
> ○ not run     spec · CLAUDE.md refresh
> ```

`✔` happened · `○` did not, by design · `✖` failed. **A fact with nothing to report collapses or disappears** — never a line reading `None.`, and several unremarkable no-ops become one `○ clean  <what you checked>`. But a no-op the reader would assume happened keeps its line — `○ not run  <what, and why>` — because silence there claims everything ran.

Then `→ Next`, last and alone: the first executable ask's exact command, or `pick an option in <n>, then <the command that resumes>`, or the one command that runs next.

**Nothing outside the three zones.** No preamble, no closing observations, no invented heading.

## Mode B — List & status (no argument)

Glob `docs/epics/*.md`. If none: say "No epics yet — open one with `/esq:epic new <title>`." and stop.

Read each epic's doc for `Status`, `Title`, `Slug`, `Goal`. Then compute every rollup from **two passes, not two per epic** — Mode C's scans are written for one slug, so running them per epic re-reads the whole plan corpus and the whole backlog once per epic:

1. One pass over `docs/plans/*.md` (excluding `*.brief.md` / `*.log.md`), classifying each plan by Mode C's rules and grouping by its `**Epic:**` slug.
2. One read of `docs/BACKLOG.md`'s rows, grouped by the `Epic` cell (read by column header).

Each rollup is then a lookup:
- **Plans:** count member plans and how many are complete / in-progress / not-started.
- **Backlog:** count tagged items that are `Open` / `Needs-decision` (skip Planned/Done/Dropped for the headline count).

### Output
```
⚠  epic — 3 epics · 2 active · 1 done · NEEDS YOU (1)

  1  Answer billing-overhaul's blocked backlog item   → /esq:backlog

  🟢 billing-overhaul   Move all billing onto the new ledger
       Plans: 3 (2 complete · 1 in-progress)   Backlog: 4 open, 1 need-decision
  ⏸ onboarding-v2      Rebuild first-run so activation clears 60%
       Plans: 1 (in-progress)                  Backlog: 2 open
  ✓ search-revamp       (done 2026-05)

→ Next: <one move>
```

Sort Active first, then Paused, then Done/Dropped. Use 🟢 Active · ⏸ Paused · ✓ Done · · Dropped. Epic is a view rather than a run: the headline's counters are the portfolio, `NEEDS YOU` counts epics with a `Needs-decision` item, and the epic list is zone 3 — it does not collapse, because it *is* the thing being asked for.

### → Next
Suggest exactly one move:
- Any epic with `Needs-decision` backlog items → `"Resolve the blocker(s) on <slug>: /esq:backlog to answer them."`
- Else an Active epic whose current plan is complete but open backlog remains → `"Next slice of <slug>: /esq:grill (to shape) or /esq:plan the next plan, then tag it **Epic:** <slug>."`
- Else an Active epic with an in-progress plan → `"Continue <slug>: /esq:build its active plan (see /esq:status)."`
- Else → `"Epics on track. Open a new one with /esq:epic new <title> when a theme outgrows a single plan."`

This mode is read-only — no file writes.

## Mode C — Show / refresh / update (argument starts with an epic slug)

Resolve the slug against `docs/epics/`. If no doc matches, say so and stop — never silently create one (that's Mode A, and it needs a title).

**Always rebuild the generated views first**, whether or not a change was requested — showing a stale epic helps no one.

### Rebuild the generated views (scan, never invent)

**`## Plans`** — Glob `docs/plans/*.md`, excluding `*.brief.md` and `*.log.md`. Select those whose top-of-file carries a line matching `**Epic:** <slug>` (this slug, leniently). For each selected plan, derive its state:

<!-- shared:plan-state:start -->
A plan's state comes from its own `## Execution log`: **complete** when every `### Phase N` heading under `## Phases` has a matching `### Phase N — completed` entry; **in-progress** when some phases are logged but not all, including any headed `⏸` — the glyph is what marks a pause, whatever clause follows it; **not started** when none are.
<!-- shared:plan-state:end -->

Write one line per plan, newest first (by filename date):
`- docs/plans/<date>-<slug>.md — <plan title> — <not started | in-progress | complete>`

**`## Backlog`** — Read `docs/BACKLOG.md` if present. Read cells **by column header** (an older backlog may lack the `Epic` column entirely — then no items match, and that's fine). Select rows whose `Epic` cell equals this slug. List them grouped, `Needs-decision` first, then `Open`; omit `Planned`/`Done`/`Dropped` from the live list but note their count as history:
`- B-012 — <summary> — Open`

Replace the entire body of `## Plans` and `## Backlog` with the freshly-scanned content. If a section comes back empty, write a single italic line (`_No plans tag this epic yet._` / `_No open backlog items._`) rather than leaving it blank or inventing entries.

### If a change was requested (text follows the slug)
Interpret it (natural language or keyword; several may combine):
- **Status** — `active` / `paused` / `done` / `dropped`, or "mark done", "park it" (→ Paused). Set the `Status` line and, on a status change, append a `## Log` line dated today (`<today> — Status → Done.`).
- **Goal** — `goal: <text>` or "goal is …". Replace the `## Goal` body.
- **Scope** — `scope: <text>` / "in scope: …" / "out of scope: …". Add or adjust a `## Scope` bullet; don't discard existing bullets unless the user says "replace".
- **Log** — `log: <text>` or free-form prose that's clearly a milestone. Append a dated bullet to `## Log`.
- **Rename** — `title: <text>` / "rename to …". Replace the title. Do **not** change the slug (it's the join key — renaming it would orphan every plan and backlog item pointing at it). If the user really wants a new slug, tell them that means a new epic.

### Output
- If only showing (no change): print the epic — Title, Status, Goal, the refreshed Plans and Backlog rollup, and the last few Log lines. End with a one-line `→ Next` echoing Mode B's logic for this single epic.
- If a change was applied: one-line confirmation, e.g. `billing-overhaul → Done; logged.` or `onboarding-v2 → goal updated; Plans/Backlog refreshed (1 plan, 2 open items).`

### Commit
If the file changed (a refresh that updated the generated views counts, or any narrative edit): `git add docs/epics/<slug>.md && git commit -m "epic: update <slug> (<what changed>)"`. If the scan produced no change at all (pure show), don't commit.

If a change instruction is genuinely ambiguous (you can't tell which field is meant), ask one short clarifying question rather than guessing — this mode mutates durable narrative.

## Template

**Epic doc** (`docs/epics/<slug>.md`):

```markdown
# Epic: <Title in plain English>

<!-- Epic: a theme spanning multiple plans over time. Managed by /esq:epic. -->
<!-- Join key: the slug below. It appears in BACKLOG.md's Epic column and as an -->
<!-- **Epic:** <slug> line under the title of each plan that belongs to this epic. -->
<!-- Slug: <slug> -->

**Status:** Active
**Started:** <YYYY-MM-DD>

## Goal
One–two sentences: the outcome this epic drives toward, observable from outside.

## Scope
- What's inside this epic's ambit.
- What's explicitly out, so the theme doesn't sprawl.

## Plans
<!-- GENERATED by /esq:epic — rebuilt by scanning docs/plans/ for **Epic:** <slug>. -->
<!-- Do not hand-edit; your changes are overwritten on the next refresh. -->
_No plans tag this epic yet._

## Backlog
<!-- GENERATED by /esq:epic — rebuilt by scanning BACKLOG.md's Epic column. -->
<!-- Do not hand-edit; your changes are overwritten on the next refresh. -->
_No open backlog items._

## Log
<!-- Milestones, human-written. Appended over time, newest at the bottom. -->
- <YYYY-MM-DD> — Epic opened.
```

## Constraints

- Touches one file only, is read-only against plans, the backlog and code, and runs no other esq command — stated in full at the top of this file, and it binds every mode.
- The slug is immutable — it's the join key. Renaming the title is fine; changing the slug means a new epic.
- If a git repo isn't initialized, write the file but skip the commit and say so.
