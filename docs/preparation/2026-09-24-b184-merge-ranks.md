# B-184 — Merge independent captures without losing stored order

Date: 2026-09-24. Starting commit: `8e934c5`. Maintainer implementation,
not an independent review or a native model trial. Local only; no installation,
push or publication.

## Evidence reused and correction

The [B-003 record](2026-09-24-b003-retained-branch.md) already establishes the
failure: independent B-1000 and B-2000 each receive Rank 100, both merges seal,
then validation reports a duplicate rank. That diagnosis is reused, not rerun.
Its historical failed/PASS audits remain unchanged.

The existing merge seal now repairs equal numeric ranks after resolving table
hunks and checking markers. It keeps ascending stored rank, breaks a tie with
the destination's row first, then numbers that sequence at the existing sparse
spacing. It neither sorts by priority/ID nor calls the ranking verb that can
promote suggested priorities. Blank legacy ranks remain unclassified. Only
changed Rank cells are written through the existing atomic writer and reported
in `applied` with rule `rank-collision`.

Before writing, compare this sequence with both branch tips and the merge base.
Every new or changed ordering relation must survive. A relation unchanged from
the base may yield to the other branch's move. A side already carrying duplicate
ranks, invalid merged numbers, or a placement this repair would reverse yields
an `ask`; no rank repair is written on that path. The attended merge remains
held; unattended landing uses its existing abort path.

The old `derive` fallback silently preferred the destination when both sides
changed the same Rank. It now asks for the intended order. Equal and one-sided
cell changes still use their existing rules. A divergent cell alone does not
prove an intention conflict: even a compatible renumbering may require context.
This deliberately conservative cell rule does not invent a general three-way
sequence solver. Similarly, moved anchors can require an explicit placement
resolution even where some combined order would be possible. The skill now
describes these outcomes; the stored-rank decision records the clarification
under the user's B-184 mandate.

## Verification scope and cost

The existing real-Git B-003 test now also asserts B-2000=100, B-1000=200,
unchanged priorities, and whole-ledger validity after both merges. No duplicate
fixture or new capture harness is needed.

Four real-Git merge regressions cover:

- Independent deliberately ordered sequences opposite ID/priority order:
  unattended landing preserves each sequence and every priority, yields unique
  ranks, validates, and leaves the source commit unchanged.
- A clean, marker-free Git merge of different IDs carrying the same tail rank.
  This does not claim B-005's ancestor-present duplicate-ID case is fixed.
- Opposing moves of one existing item: unattended `ask` restores the original
  repository; attended sealing retains markers until an explicit resolution.
- A new placement relative to an anchor moved on the other side: refuse to
  reverse that placement, then abort restores the original repository.

The existing cell-level test now pins one-sided preservation and divergent
Rank refusal. All these tests run through the product audit, not a separate
Node invocation beside it.

Cost: one backlog read at sealing; only a collision adds three Git blob reads,
sorting, and at most quadratic comparisons in the number of ranked rows per
side. No history walk, dependency, subagent, network query, telemetry, registry,
schema, CLI verb or general reconciliation layer. The gain is avoiding manual
repair of neutral collisions; no runtime speedup is claimed. The audit is
bounded to 180 seconds and requested outside the sandbox on the already
documented B-003 child-process restriction.

## Result

One native `./scripts/audit.sh`, under the 180-second bound: **7/7 PASS**,
including product suites and native package validation. [Captured
output](2026-09-24-b184-audit.txt). No standalone suite was run before or after
it on this implementation. The historical B-003 audits were not rerun.

Observed regression result: B-2000 keeps Rank 100 and B-1000 receives Rank 200,
with both IDs, summaries and `med?` priorities preserved; validation succeeds.
The deliberate sequences B-090 → B-010 and B-080 → B-020 remain intact after
interleaving, despite their opposite ID/priority order. Conflicting positions
are not silently selected: the unattended path aborts, and the attended path
can seal the explicitly resolved order.

B-184 is closed through `esq backlog set-status` with this evidence; B-005 stays
Open. This is inline work, so no retrospective plan or execution log is created.
Only bookkeeping changes follow the product PASS. `esq validate` returned
`valid: true` with no findings, and `git diff --check` passed before the local
commit. The product proof is reused, with no second audit.
