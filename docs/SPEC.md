# Spec — esquisse
<!-- last-spec: 2026-09-20 @ b064879e8431af9db3d43542b21fddd6f9580285 -->

> Ce document décrit ce que le produit fait, du point de vue d'un product owner. Il est généré et mis à jour par `/esq:spec`.
> Dernière mise à jour : 2026-09-20

## Vue d'ensemble

esquisse is a Claude Code plugin (`/esq:*`) that turns software work into a cycle of short, focused sessions — interrogate, plan, build, verify, review, fix, land — with every step leaving a committed artifact (a brief, a plan file, a ledger row, a report) so the next session, or another person, picks up from the file rather than from memory. It is for developers who run Claude Code on a real codebase and want the work to stay cheap, inspectable and bounded: each command states what it will spend before spending it, asks only questions the repository cannot answer, and never chains into another command on its own.

## Fonctionnalités

### Interrogation — `/esq:grill`
**Résumé:** Kills ambiguity in a vague request before anything is planned, and writes a brief.
**Utilisateurs:** The developer, at the start of a task that is not yet crisp.
**Fonctionnement:** Reads the codebase and the product spec, answers for itself whatever the repo settles, researches outside practice for anything below the product/architecture line, then asks the user the remaining questions — each with a recommended answer. Writes `docs/plans/<date>-<slug>.brief.md` (including a `## Done looks like` section in the user's own words), commits it, stops.
**Règles métier:**
- **Asks only for an authority nobody recorded, never by subject.** A question is owed when a preference or authorization the repository does not carry would change the product outcome, the scope, a major architecture commitment, a stated constraint, or a cost or risk nobody approved — and the ask names which. Several viable options, plain uncertainty, or the fact that the subject is *UX* or *architecture* is not enough on its own: that gets decided and recorded. Implementation details (libraries, test runners, versions) are never asked — they are researched and cited with their date. <!-- modifié 2026-09-19 : « ne demande que l'intention, le scope, le produit, l'architecture ou l'UX » → le seuil est une autorité manquante et nommée, pas un sujet (D-a-question-needs-a-missing-authority) -->
- **Un besoin d'interface sans interface existante est routé vers le mode greenfield.** Quand le brief décrit un produit dont l'UI n'est pas encore écrite, la suite proposée est `/esq:ui --greenfield <brief>`, qui rendra deux directions depuis le contenu que ce brief porte déjà. <!-- ajouté 2026-09-20 -->
- Read-only apart from the one brief it writes.

### Planning — `/esq:plan`

<!-- mis à jour 2026-09-01 : le plan enregistre sa branche dans l'en-tête (`**Branch:**`) -->
<!-- mis à jour 2026-09-02 : le référent d'une étape `(auto)` est résolu par lecture à l'écriture du plan (B-106) -->
<!-- modifié 2026-09-05 : `**Branch:**` valait la branche d'invocation → le plan taille `esq/<slug>` et enregistre la branche d'invocation dans `**Origin:**` (D-a-shipping-unit-lands-where-it-started) -->
<!-- mis à jour 2026-09-08 : le plan s'auto-audite en huit points avant de se présenter et de se committer -->
<!-- mis à jour 2026-09-11 : le plan retire le brief correctif qu'il planifie, dans son propre commit (D-plan-retires-the-brief-it-plans) -->
<!-- mis à jour 2026-09-13 : l'auto-audit passe de huit à neuf points — une vérification obligatoire n'achète jamais deux fois la même preuve, et la règle est aussi énoncée à l'écriture des étapes (D-a-phase-buys-each-proof-once) -->
**Résumé:** Produces the plan file that every later step treats as the contract.
**Utilisateurs:** The developer, once the task is crisp (or from a brief).
**Fonctionnement:** Reads the codebase, the brief if one exists, the spec sections the task touches and the backlog; cuts the plan's own branch `esq/<slug>` from the branch it was invoked on, and writes `docs/plans/<date>-<slug>.md` there with context, goal, approaches, phases with tasks and tagged verification steps, risks and open questions. Remaining open questions are asked at the end as a questionnaire and folded back in. Commits and stops.
**Règles métier:**
- `## Goal` must name what a user can do afterwards; a plan whose outcome is invisible to users must say what user-facing work it unblocks.
- A right-sizing audit cuts generality nobody has a caller for (single-implementation abstractions, unread flags) and offers it to the backlog instead — but never trims a trust boundary, an error state or a data model a requirement already needs.
- Backlog items overlapping the task are marked `Planned by <slug>`; a real choice made during planning is recorded in the decisions registry.
- A task that changes a documented spec rule is named as a product change; one that contradicts a rule becomes an open question before phases are written.
- `(manual)` verification steps must be written so a browser driver could run them (route, visible label, on-screen result).
- A Node verification step names explicit test files or a quoted glob, never a bare directory: on Node 22 a bare directory is resolved as a module and the run fails before a single test executes, so a suite that would have passed is read as one that failed. One bad operand among valid ones reds the whole step.
- **An `(auto)` step's command is resolved before the step is written — by reading, never by running it.** The script or executable has to exist and be executable, and the argument shape has to be one that script's own documented usage accepts (its usage header, its `--help`, or its existing call sites, in that order). A path the plan's own tasks create counts as resolved. Running the command to check it is never the way: planning does not execute the planned work, and a step naming a whole-repo suite would cost minutes per plan for a signal reading already buys.
- **A phase's mandatory verification buys each proof once.** Before a phase's `(auto)` set is final, what each command actually selects is read — the package script it resolves to, the paths and config that decide which tests run, the environment it sets — and a step whose tests *and* whose PASS criterion another required step of the same phase already buys under equivalent conditions is not declared: the broader command is prescribed alone. The narrower run stays useful while building and its result is recorded in the execution log; it simply does not become a second landing obligation. Both steps are kept whenever the narrower proves something the broader does not — a typecheck, a lint, a different environment or runner, a flag that changes what is asserted, a negative control — and whenever the inclusion cannot be settled by reading. A command's name is never proof of coverage. This decides one phase's own set and nothing else: an earlier phase's targeted step survives a later phase's whole-repo run, and a plan already written keeps every obligation it declared. <!-- ajouté 2026-09-13 (D-a-phase-buys-each-proof-once) -->
- **Une étape `(auto)` peut déclarer ce que sa commande lit, et la déclaration est une promesse.** Après la phrase qui nomme la propriété vérifiée, une étape peut lister les chemins du dépôt que sa commande lit ; l'atterrissage juge alors la fraîcheur de *cette seule commande* contre ces chemins-là, et cesse de racheter une suite que l'unité d'expédition n'a jamais touchée. La déclaration est facultative et son absence est le défaut — c'est ainsi que tout plan déjà écrit est jugé. Elle n'est écrite que si la lecture tranche : le plan lit le fichier exécuté, ses imports, ses fixtures et sa configuration, et s'abstient partout où cela ne se règle pas par lecture — une commande non déclarée coûte des minutes, une commande sous-déclarée coûte la régression qui atterrit sans preuve. Jamais pour un garde qui lit tout le dépôt, dont la seule déclaration honnête nommerait le dépôt entier. <!-- ajouté 2026-09-14 (D-a-step-declares-what-it-reads) -->
- **Each `(auto)` step's sentence names the artifact and the property being checked**, not a bare command. That sentence is the only thing the build can fall back to when the command turns out unrunnable, so a step that is only a command is ambiguous by construction and halts the phase instead of completing it.
- **The plan cuts its own branch and records the pair that makes a shipping unit.** `**Origin:**` is the branch it was invoked on — where this unit's work lands when it is done — and `**Branch:**` is `esq/<slug>`, cut from that origin so the plan file's own commit is the first thing on it and the origin is left as it was found. Both fields belong to this command alone among commands; no later command rewrites them. A corrective `-fixes` plan copies its stem's two fields and cuts nothing — stem and sibling are one shipping unit. An `esq/<slug>` that already exists stops the command by name rather than being attached to or uniquified: the collision means the work already has a shipping unit, and which one was meant is the user's to say. On a detached HEAD or outside a repository both fields are omitted, which leaves the plan `unrecorded` (it still builds) and legacy (it never lands).
- **The plan audits itself before it is presented or committed** — one pass, in the context already held: no subagent, no extra artifact, no re-read of a file the run has already read. Nine checks: no lifecycle step another command already owns; implementation completion stated apart from any measurement only taken after the ship; `## Done looks like`, the scope exclusions, the phases and `## Risks` not contradicting each other; any widening of a public schema or data surface made explicit; boundary values and malformed input covered by a phase; activation and deployment named where the user only gets the change after an install or a restart; every `(auto)` command resolved against its own script's documented usage; no phase's mandatory verification buying one proof twice; every phase within the four-task limit. An ordinary omission is corrected in place and mentioned in one line — only a genuine product-policy choice ever becomes a question, and it rides the questionnaire already being sent rather than buying a round trip of its own. The point is that a plan's ordinary omissions would otherwise cost a full `/esq:check` subagent, one command and one session later.
- The plan names its own branch and origin in the header, cuts that branch, and commits itself there. Its closing summary names the next command — `/esq:build` for Phase 1, or `/esq:autopilot` when it has two or more phases.
- **Deux générations correctives, et la troisième n'est pas la sienne à ouvrir.** Avant d'ouvrir un nouveau tour correctif, la commande demande au CLI à quelle génération la chaîne se trouve. Épuisée — deux tours ont déjà atterri sur cette unité — elle refuse d'écrire le plan correctif et rend une seule décision à l'utilisateur : accepter ce qui tient (les items sûrs sont appliqués, le reste devient de la dette écrite) ou abandonner l'unité et replanifier depuis le plan d'origine. Aucune constatation n'est perdue : le brief reste sur le disque et continue de bloquer l'atterrissage jusqu'à ce qu'il soit traité. <!-- ajouté 2026-09-20 (D-corrective-generations-bounded-at-two) -->
- **A corrective brief the plan consumed is retired in the plan's own commit.** Planning from a fixes brief strikes the 🟡 items it planned and any 🔴 it resolved with the user; when nothing is left the brief is deleted, otherwise it stays with its unapplied 🟢 or undecided 🔴 intact — those still belong to `/esq:fix` and to the user. An interrogation brief is never touched. Without this, a planned brief left on disk made `/esq:land` refuse the unit forever and send the user back to planning work that already had a plan. <!-- ajouté 2026-09-11 (D-plan-retires-the-brief-it-plans) -->

### Building — `/esq:build`
<!-- modifié 2026-09-10 : « pause seulement quand aucun instrument n'existe » → une seconde cause de pause, un défaut de la même unité d'expédition resté ouvert (D-a-same-unit-defect-is-never-a-backlog-row) -->
<!-- mis à jour 2026-09-10 (bis) : la pause bloquée a une sortie bornée, et les candidats backlog sont déposés avant l'entrée de log (U-10, U-11) -->
<!-- mis à jour 2026-09-09 : une vérification lancée en arrière-plan est collectée une fois, sous une borne, et tout processus lancé est confirmé mort avant le log -->
<!-- mis à jour 2026-09-01 : refus d'une branche que le plan ne possède pas, avant toute lecture -->
<!-- mis à jour 2026-09-02 : deux exceptions comptées à « exécuter l'étape telle qu'écrite », dont la commande inexécutable (B-106) -->
<!-- mis à jour 2026-09-20 : une panne diagnostiquée est réparée sur place, sous un budget que le rapport imprime (D-a-repair-budget-replaces-the-ceiling) -->
**Résumé:** Executes exactly one phase of a plan, with atomic commits and an execution-log entry.
**Utilisateurs:** The developer, one invocation per phase, `/clear` between.
**Fonctionnement:** Finds the next phase, implements each task as its own commit, runs the phase's verification, appends a `### Phase N — completed` entry to the plan's execution log and stops — it never auto-advances. Out-of-scope observations are filed as backlog rows carrying where they came from; on the last phase it closes itself the rows the plan picked up whose whole outcome was delivered and verified, and leaves the rest open. <!-- modifié 2026-09-11 : « liste les lignes `/esq:backlog B-N done` » → ferme lui-même ce que sa vérification prouve livré (D-evidence-settles-backlog-dispositions) -->
**Règles métier:**
- **Never self-certifies a `(manual)` step.** It first looks for an instrument (a run/verify skill or a browser-driving server) and observes the screen itself; it pauses (`⏸ awaiting manual verification`) — the first of the two pause causes below — only when no instrument exists at all, and says which ones it looked for. When it had to improvise a harness, the recipe goes in the log and a backlog candidate proposes a project run skill. Finding a project skill normally closes that candidate — unless the skill fails on its own environment (an invocation that opens by installing something the caller must revert, or a path the caller has to assemble), in which case the finding stands against that skill's setup. <!-- mis à jour 2026-08-21 : un slot rempli par un skill défaillant reste une constatation (B-069) -->
- **Refuses a branch the plan does not own, before reading anything.** The ownership verdict is asked for in preflight, ahead of the plan file itself, so a refusal costs one command and not the read it prevents. It stops there and hands back the options; it never switches a branch or edits the plan header.
- **Reconciles before building.** If a previous run committed every task of the phase and died before logging it, build re-runs the phase's `(auto)` verification: green → logs the phase as `Reconciled:` and continues into the next one (at most once per run); red → builds it normally. Verification decides, never commit-subject matching alone.
- **Une pause se résout par un seul verbe, quelle que soit sa cause.** À la reprise : toutes les étapes observées PASS par le build → la phase passe à complétée et la session continue ; toutes confirmées PASS par l'utilisateur → elle passe à complétée et la session s'arrête ; un seul FAIL → la pause reste en place. Le passage est écrit par la même commande déterministe qui libère une pause bloquée, jamais par une entrée de journal réécrite à la main, et il ne rachète rien : il réutilise ce que la pause avait déjà prouvé et ne relance que ce que le dépôt ne peut plus prouver. <!-- mis à jour 2026-09-14 : la bascule passe par le verbe qui libère déjà la pause bloquée (D-one-verb-resolves-both-pause-clauses) -->
- Runs the narrowest verification that would still catch the failure; never re-runs a check that already passed unchanged; writes verification cost in the log when it exceeds a couple of minutes.
- **A verification launched in the background is collected once, waited on under a bound, and torn down before the phase is logged.** A finite check has exactly one result: it is read a single time rather than polled with a call that asks the question the previous call already asked, and the wait either names a deadline it will not outlive or blocks on the run actually finishing — never an open-ended loop with nothing to stop it. Before the execution-log entry is appended, every process the phase started is confirmed gone. What that teardown does *not* reach is stated with it: it does not clear the harness's own registration of the task, so a late notification can still arrive at a phase that has concluded, and such a notification is never resurrected into live work. Collecting a result late, or after a bound expired, does not change its colour — a red is still a failed phase. <!-- ajouté 2026-09-09 -->
- **Two exceptions to running an `(auto)` step exactly as written, and only two** — the count is itself the guard, so a third has to argue with a number. The first is the whole-repo suite a phase's blast radius does not earn, narrowed to what the phase touched. The second is a command that cannot run as written — its script missing or not executable, its argument shape one that script's usage refuses, or a different artifact than the step's prose names — where the step's own sentence names the artifact and the property: the check that prose describes is run instead, at the same or greater strictness, never a narrower check and never a different property. Both substitutions are recorded the same way in the execution log: the command run, the command the plan named, and why the plan's could not do the job. An unrunnable step is additionally filed as a backlog candidate against the plan that shipped it.
- **An unrunnable command whose intent cannot be recovered fails the phase.** Where the step is only a command, or its prose names no artifact and property, or two readings would run different checks, the build says the command could not run as written and stops — it never substitutes a check the step did not describe.
- On the last phase, the hand-off is a constant: `/esq:review <plan-path>` in a fresh session, with `/esq:converge <plan-path>` named as the unattended form at its real cost. <!-- mis à jour 2026-09-22 : la lane ne choisit plus la sortie -->
- **A defect against the unit being shipped cannot be parked in the backlog.** *Out of scope* means outside the shipping unit — every plan recording the same branch — not outside the phase. A bug or a piece of debt in code the unit wrote is corrected inside the phase when it is an ordinary omission, and pauses the phase when it is substantive; it is never written down and left behind while the phase reports itself complete. Before this, such a row went nowhere a later step could read it, and the only way a defect came back was a paid reviewer happening to rediscover it. <!-- ajouté 2026-09-10 -->
- **Second pause cause: an open defect of the same shipping unit.** A bug or debt backlog row whose source names a `build:` or `fix:` step of this unit, and whose status is neither Done nor Dropped, stops the phase completing — it is logged `⏸ blocked on an open same-unit defect`, naming the rows, and the entry itself is refused rather than written. Each row is then disposed of — closed Done by the build itself when a commit of the unit fixed it and a passing check verified it, or Dropped by the user, with its reason, when deliberately accepted — and the phase is released by the transition below rather than rebuilt. <!-- modifié 2026-09-11 : « l'utilisateur dispose de chaque ligne » → le build ferme ce que ses preuves établissent ; l'acceptation reste à l'utilisateur (D-evidence-settles-backlog-dispositions) --> The test is the row's source cell, not where the failure lives: it therefore also stops a phase on a defect the unit filed about code it never touched, which is deliberate — it blocks wider than the rule reads and never narrower. An idea never blocks, and neither does a row a reviewer filed. <!-- ajouté 2026-09-10 -->
- **A pause is recognised by its `⏸` glyph, never by the words after it.** Both causes are the same state to every command that reads an execution log, and a third would need no rule change anywhere.  <!-- ajouté 2026-09-10 -->
- **A blocked pause has exactly one way out, and it re-implements nothing.** Once every blocking row reads Done or Dropped, the next build releases the phase instead of rebuilding it: the phase's commits are already in the tree, so no task is written a second time. It re-uses the verification results the repository can still prove describe the current state, runs only the checks it cannot prove, and judges each against what the step says rather than against a bare success code; any red leaves the phase blocked. The released entry keeps the blocking rows with the disposition and reason recorded for each, then reads completed — or stays paused for manual steps still owed, settled in the same run. While any row is still undisposed, and on every other refusal (a row that was deleted, a pause of the other kind, an entry already released), the plan file is left byte-for-byte as it was, so an interrupted resolution costs only the checks it had not yet re-run. <!-- ajouté 2026-09-10 -->
- **This phase's backlog candidates are filed before its execution-log entry is written, and the order is the rule.** A defect the phase found is deposited and its status recomputed first, so the entry it writes has to face it; filing afterwards is exactly how a defect against the unit got parked while the phase that found it reported itself complete. A run interrupted between the two lands on the blocked pause on its next attempt, re-implements no task and files no row twice. <!-- ajouté 2026-09-10 -->
- **A finding is classified when it is filed, from evidence, and never to get past the gate.** It is filed as *observed* — a source that blocks nothing — only when it lies outside the promised work, fails the same way on the branch the unit started from, and nothing the unit changed (callers, data, configuration, interfaces) reaches or worsens it. An untouched file does not prove that, since a changed caller can break an unchanged consumer, and neither does a failure that pre-dates the unit, which the unit may have aggravated or promised to fix; a finding that cannot be placed blocks. No row is dropped, re-filed or re-classified to let a phase complete. <!-- ajouté 2026-09-11 (D-evidence-settles-backlog-dispositions) -->
- **Done means delivered and verified.** A row the plan picked up is closed only when its whole promised outcome shipped and a check proved it; partial delivery stays open, and the closing records what delivered it. <!-- ajouté 2026-09-11 -->
- **Une panne dont le correctif est déjà écrit est appliquée, pas rendue à l'utilisateur.** Quand une vérification échoue et que la phase sait nommer la cause, elle applique elle-même la correction au lieu de s'arrêter en affichant l'action à faire. Le budget est de **trois réparations par phase et par invocation**, et chacune doit viser une cause sur laquelle cette phase n'a pas déjà dépensé une tentative : un second rouge de la même cause est un épuisement, pas une nouvelle tentative. Le compte est imprimé — `repairs <n>/3` — sur le rapport d'échec **et** sur la ligne de succès d'une phase qui a réparé, parce qu'une phase qui a réparé et terminé quand même doit le dire. Trois causes distinctes dans une seule phase, c'est le moment où le suspect est le plan et non le code. Le budget ne vit qu'à l'intérieur d'une invocation : aucun orchestrateur ne relance une panne déjà rapportée. <!-- ajouté 2026-09-20 (D-a-repair-budget-replaces-the-ceiling) -->
- **A phase cannot report itself complete without saying what proved it.** Where the phase's verification names at least one runnable automatic check, the completion is refused unless it records the exact tree the checks ran on and the exact commands whose whole step was judged a pass. The refusal arrives in the same breath as the completion — while the evidence is still live — rather than from a later sweep, when the only honest repairs left would be re-running the work or inventing it. What is required is the record, never its contents: a phase is free to have substituted a command, and nothing compares the two lists. A phase that cannot state both halves honestly pauses or fails; seule la pause *bloquée* peut encore dire qu'elle s'est arrêtée avant de juger — une pause qui n'attend plus que des étapes manuelles a committé son code et jugé chacune de ses vérifications automatiques, donc elle doit enregistrer les deux moitiés exactement comme une phase complète, et l'oubli est refusé de la même façon <!-- modifié 2026-09-14 : « toute pause garde le bloc facultatif » → la pause manuelle le doit (D-a-manual-pause-records-what-proved-it) -->, and a phase whose verification is manual only, or names no runnable check, is asked for nothing. Without this, a phase that ran its checks and forgot to record them was accepted in silence, and the landing re-bought the whole suite over a tree already proved green. <!-- ajouté 2026-09-12 (D-a-completed-phase-records-what-proved-it) -->

### Gap analysis — `/esq:check`
**Résumé:** Compares what was planned with what shipped. Read-only.
**Utilisateurs:** The developer, after the last phase.
**Fonctionnement:** Reads the plan, its execution log and git history; reports a verdict (ship / fix specific things / rework) and, when there is something to fix, writes a fixes brief with findings triaged 🟢/🟡/🔴.
**Règles métier:**
- First question, before per-phase audit: **does the result answer `## Done looks like`?** A plan that shipped every task but solves the wrong problem gets that verdict, and it outranks "matches plan".
- A paused (`⏸`) phase counts as not done — whichever of the two causes stopped it, an unobserved manual step or an open same-unit defect; a phase marked completed whose manual steps were excused in prose is flagged 🚩 false-complete. <!-- mis à jour 2026-09-10 : la pause a une seconde cause -->
- Divergence from the planned route is not a finding unless it changed the outcome.
- Includes a spec-conformance pass: shipped behavior vs. documented rules, and features the spec has fallen behind on. Disagreement is reported 🔴 and asked — never assumed to be the spec's fault.
- **Le `→ Next` est calculé contre la borne corrective.** La commande écrit son brief comme d'habitude, mais quand la chaîne a déjà consommé ses deux générations, elle ne propose plus d'en ouvrir une troisième : elle route vers la même décision utilisateur — accepter ce qui tient, ou abandonner et replanifier. <!-- ajouté 2026-09-20 (D-corrective-generations-bounded-at-two) -->

### Adversarial review — `/esq:review`
<!-- modifié 2026-09-11 : « une re-review se limite au delta depuis le stamp du brief » → depuis le commit le plus récent qu'une review a lu — stamp d'un brief de review ou couverture d'une review propre, jamais celle de /esq:converge (D-review-delta-base-is-a-reviews-own-record) -->
**Résumé:** Reviews the implementation for bugs, edge cases, security and design flaws, independent of the plan.
**Utilisateurs:** The developer, after the build; re-runnable after fixes.
**Fonctionnement:** Reads the code the plan touched, checks it against each documented business rule in the spec, writes findings 🟢/🟡/🔴 into `<plan>-fixes.brief.md` stamped `Reviewed at: <hash>`. A re-review scopes to the delta since the newest commit a previous review actually read — a review brief's stamp, or the coverage a clean review recorded — unless the user says "full re-review". `polish` drops the bar to "genuinely better" for an exhaustive sweep.
**Règles métier:**
- **Every finding must name a failure** — who hits it, under what condition, what goes wrong. Taste-level cleanups are dropped, not softened or filed.
- 🟢 means a defect with a mechanical fix — safety alone never makes something a finding.
- A documented spec rule the code silently violates is a real bug.
- **A clean verdict is recorded as review coverage.** When nothing clears the bar in any tier, the review writes the commit it covered into the plan header — the only plan-file edit it ever makes, never by hand — and hands off to `/esq:land`, which refuses a tree that coverage no longer describes. A verdict with any finding records nothing: the fix, and the review of it, come first. <!-- ajouté 2026-09-11 (D-a-landing-reads-coverage-and-obligations) -->
- **A re-review narrows only to what a review read.** The coverage `/esq:converge` records is never a starting point, because it covers the loop's last fixes, which no review read — narrowing past it would leave them unreviewed for good. A brief or record belonging to a different plan, including the plan's own `-fixes` sibling, never counts; a starting point that history no longer contains (a rebase, a squash) is dropped; and with none left the review reads the whole unit. When only bookkeeping changed since the starting point, the review opens no file, reports clean and records coverage — the re-review a landing asks for after a clean review costs that change, not the unit. <!-- ajouté 2026-09-11 (D-review-delta-base-is-a-reviews-own-record) -->
- **Le `→ Next` est calculé contre la borne corrective.** La commande écrit son brief comme d'habitude, mais quand la chaîne a déjà consommé ses deux générations, elle ne propose plus d'en ouvrir une troisième : elle route vers la même décision utilisateur — accepter ce qui tient, ou abandonner et replanifier. <!-- ajouté 2026-09-20 (D-corrective-generations-bounded-at-two) -->
- **What a review reads is answered once, and doubt widens it.** The range under review — the commit it stops at, whether it is a whole-unit read or a delta, the starting point and why that one — comes from a single read-only answer rather than being worked out by the reviewer. Any failure to settle it answers the whole unit, never a narrower range. <!-- ajouté 2026-09-16 (D-review-scope-is-one-deterministic-query) -->

### Applying safe fixes — `/esq:fix`
**Résumé:** Applies the 🟢 items of a fixes brief and escalates the rest.
**Utilisateurs:** The developer, after check or review wrote a brief.
**Fonctionnement:** Reads the newest fixes brief, re-validates each 🟢, applies it, verifies, commits atomically; rewrites the brief with only 🟡/🔴 left and reports counts (fixed / need a plan / need your decision).
**Règles métier:**

- 🟡 items are escalated to the backlog as `⚠️ debt`; 🔴 as `Needs-decision`, each arriving as lettered options with a runnable `do:` and a leaning — never as a bare question.
- It closes the backlog row a green fixed itself — only when the row asks for exactly what was fixed and verification passed, recording the fix and its commit. - **Emptying a review's brief hands back to review, never to landing.** When every item of a brief a review wrote is resolved, the next step named is a review of that same plan — the fixes invalidated the review's verdict, and only a review re-establishes it. ### Ce qu'une revue achète — `/esq:review`, `/esq:converge`
<!-- remplace « Niveau d'assurance » le 2026-09-22 : le bloc `## Assurance`, les quatre lanes, leurs axes et leurs statistiques sont retirés — les quatre lanes portaient le même itinéraire depuis 2026-09-09, la lane ne décidait donc plus que la recommandation autonome, et cette recommandation est désormais la même pour tout plan -->

**Résumé:** Une seule lecture couvre le travail normal : `/esq:review` établit si le changement répond à la question posée *et* si le code tient. `/esq:check` reste disponible comme diagnostic plus profond, demandé explicitement.

**Utilisateurs:** The developer, at the end of a build.

**Fonctionnement:** After the last phase, `/esq:review` reads the change — goal conformance first, then correctness, security, UX, design — and writes a corrective brief when something clears its bar, or records `**Reviewed at:**` when nothing does. `/esq:converge <plan>` is the unattended form: review, then `/esq:fix` if the brief carries a 🟢, at most two subagents. `/esq:check <plan>` reconciles the plan against its implementation phase by phase; it is worth a session on a large plan or a suspected drift, it records no review coverage, and nothing routes to it automatically.

**Règles métier:**
- **A landing needs a review, and only a review records coverage.** `/esq:check` never substitutes for it.
- **A verified fix and a clean review are recorded distinctly.** A clean `/esq:review` writes `**Reviewed at:**` under its own commit subject; a `/esq:converge` run whose fix applied everything records the unit's coverage under `plan(converged):`, because a re-review takes its delta base only from a commit a review's own clean verdict made.
- **Anything still open means not ready to land** — a 🟡 or 🔴 left in a brief, an unsettled gate, a `unit.open` row, a fixer that died.
- **`/esq:review` accepts a commit range as well as a plan.** `<A>..<B>`, or a single commit-ish meaning that commit alone, reviews a change that has no plan file — which is what an inline `/esq:work` fix produces. That review records no coverage and does not hand off to `/esq:land`: landing is plan-based.
- **A missing target is asked for, never guessed.** `/esq:review` and `/esq:check` invoked with no argument stop and ask in one line; neither takes the most recently modified plan. The run most likely to be missing a target is a small fix made without a plan, where the newest plan file is guaranteed to be the wrong answer.
- **The plan-less journey runs end to end.** The review's brief records the range it read in its `Source:`, both commits in full; `/esq:fix` applies the greens, verifies each with what the item names, records no proof into a plan (there is none), and hands back `/esq:review <base>..<its own last fix commit>` — the corrected result, not the diff the findings were raised against. It offers no landing: landing is plan-based, and an unplanned change on a branch carrying no plan is not a shipping unit.
- **A plan that still carries an `## Assurance` block is read past without comment.** Nothing parses it, nothing refuses it.

### Landing — `/esq:land`
<!-- ajouté 2026-09-11 : l'atterrissage devient sa propre commande (D-landing-is-its-own-command) -->
**Résumé:** Merges a finished, reviewed shipping unit into the branch it started from — after proving from recorded facts that it is ready.
**Utilisateurs:** The developer, once every plan on the branch is built (or recorded abandoned) and a clean review or corrective loop has covered the tree.
<!-- modifié 2026-09-11 : les prérequis portaient sur le seul plan nommé → ils portent sur toute l'unité d'expédition (D-land-verifies-the-whole-unit, D-a-unit-lands-when-every-plan-is-built-or-abandoned) ; la fraîcheur de la spec et de l'architecture passe de prérequis à avis (D-projection-freshness-is-advice-at-landing) -->
**Fonctionnement:** `/esq:land <plan>` reads every recorded fact in one pass and stops at the first prerequisite that does not hold, cheapest first — every one asked of the whole shipping unit, since the merge takes the whole branch, so the answer is the same whichever of its plans you name: already landed · no recorded origin · not standing on the unit's branch · uncommitted changes · a plan of the unit still unbuilt or paused and not recorded abandoned · a ledger that does not parse · a backlog row the unit filed or promised still undisposed · a corrective brief still carrying items · no clean review covering the current tree. Only then does it run the verification the repository cannot prove is still green across every plan of the unit, each command at most once, and — in the same breath as a last check that nothing was committed while that verification ran — makes one local merge commit. Every stop names the command that clears it. A spec or architecture document that no longer describes the tree is reported on one line naming its refresh command, and the landing goes ahead.
**Règles métier:**
- **Explicit by design.** It takes a plan path and never guesses the most recent plan — a guess would aim a merge at whatever was touched last.
- **Already landed is answered first.** A unit whose branch is already on its origin — merged, or carried over by cherry-pick or rebase — reports `already landed` and does nothing, even when inspected from the destination branch, where a branch complaint about finished work would send the user to fix something that is not broken. A unit whose branch was deleted after it landed still reads as landed, so nobody is sent to switch to a branch that no longer exists. <!-- mis à jour 2026-09-11 -->
- **Every prerequisite is a hard stop, and advice never becomes one.** A finding that looks minor, a review that "covered nearly all of it", a row that was "obviously delivered" stops the landing like any other: a merge that skipped one would land a tree nobody reviewed or a promise nobody closed. Deleting the plan file is not abandonment. An abandoned plan's promised backlog rows and live corrective briefs still block, so abandoning a plan never quietly drops what it promised. <!-- ajouté 2026-09-11 (D-a-unit-lands-when-every-plan-is-built-or-abandoned) -->

- **A live finding sends the user to the right command.** A corrective brief of the unit still on disk with items in it stops the landing; any 🔴 names `/esq:converge <brief>`, otherwise any 🟢 names `/esq:fix <brief>`, otherwise `/esq:plan <brief>`. A deleted brief counts as resolved.

Rien n'est déverrouillé, déplacé ni supprimé à la place de l'utilisateur : un checkout que cette commande ne possède pas tient le travail de quelqu'un d'autre. <!-- ajouté 2026-09-14 (D-a-landing-runs-where-the-destination-lives) -->
- **Only the tree that was verified lands.** Verification can take minutes; if anything was committed to the branch meanwhile, the landing refuses as a no-op — nothing merges — and names `/esq:land` again, since every fact it checked described a tree that is no longer the one that would merge. <!-- ajouté 2026-09-11 (D-land-verifies-the-whole-unit) -->
- **It lands where the unit started, and never pushes.** The merge reads source and destination from the plan header itself, immediately before it writes: the unit's branch lands on the branch the user was standing on when the plan was created — never a repository default, never the branch the command was invoked from. Nothing is pushed, published, released or deployed; putting the merge into service is a separate step a person runs.
- **Every refusal is a no-op.** Nothing is written, the source branch and its commits are untouched, and the report carries the command that clears the stop — for a refused merge, the exact attended `/esq:worktree merge` line the merge engine wrote, printed verbatim. The landing line is never absent: `landed`, `already landed`, or `not landed` with its reason and command.
- No subagents; one merge commit or none.

### Unattended roadmap walk — `/esq:advance`

<!-- modifié 2026-09-22 : le préflight de mesure et l'assertion de modèle après lancement sont retirés ; `model: opus` reste demandé, son respect n'est ni mesuré ni attendu -->
<!-- mis à jour 2026-08-22 : invocation ciblée `/esq:advance <slug|B-NNN>` — une seule entrée de `Now` -->
<!-- mis à jour 2026-09-10 : une entrée bloquée est sautée, pas un arrêt du run ; un `needs:` ne bloque que tant que sa cible est encore en file (D-needs-blocks-on-queue-presence, B-146) -->
**Résumé:** Works the roadmap's `Now` horizon unattended, one subagent per backlog item — the whole horizon, or one entry of it.
**Utilisateurs:** The developer who maintains a roadmap and wants its head worked while away.
<!-- modifié 2026-09-11 : « chaque item planifiable reçoit un plan, l'avance reste sur la branche du plan » → les unités existantes sont reprises telles quelles, une entrée donne au plus un plan, et l'avance revient à sa branche de départ (D-advance-preserves-units-and-its-branch) -->
**Fonctionnement:** Walks the `Now` entries in order. An item already planned — on any branch, merged or not — is handed off to its existing plan and not worked again. Every other item goes through `/esq:work`: trivial items are done and closed, blocked ones are recorded and skipped, and the items of one entry that need planning are gathered into a single new plan. After every item and every plan it returns to the branch it started on, so later commits land where they belong. Given a target — an entry's name, or a backlog ID some entry covers — it walks that one entry instead of the horizon, everything else unchanged. Refreshes the roadmap itself at the end if anything changed. Reports per item, naming each plan and the branch it lives on, and ends with the bill.
**Règles métier:**
- **Stops before `/esq:build`** — turning a plan into code is `/esq:autopilot`'s question, with the plan in front of the user.
- **An existing plan is never replaced, extended or duplicated.** A plan is a shipping unit with its own branch; a second run discovers the plans the first one wrote, even on branches not yet merged, and hands them off. One `Now` entry yields at most one new plan. <!-- ajouté 2026-09-11 -->
- **It always comes back to where it started.** After each item and each plan it switches back to its starting branch; when the tree is dirty or the switch is refused it stops with the exact blocker and the command to run once settled — it never forces a switch, stashes or discards a change. <!-- ajouté 2026-09-11 -->
- **A blocked entry is skipped, not a stop.** Only a dirty working tree, a starting branch it cannot safely return to, or a worker found running on the wrong model halts the whole walk. An item that cannot be finished — waiting on a decision, waiting on a `needs:` edge, or simply failing — is recorded and skipped, and the walk moves on, after checking whether anything further down was waiting on what just failed. <!-- mis à jour 2026-09-10 : « seul un arbre sale ou un `needs:` arrête le run » disait mal ce que fait un `needs:` — il saute l'entrée -->
- **A `needs:` edge blocks only while what it waits on is still queued** — the same rule `/esq:roadmap` applies, so the two readings of the file cannot disagree. A target still sitting in a horizon blocks; one that has shipped, one already rolled up done by this pass, and one the roadmap no longer holds at all do not. An absent target is reported as not found alongside the entry, and the entry is walked. <!-- ajouté 2026-09-10 -->
- Decides from the ledger row and `git log`, never from what a subagent said about itself; a `Done` row without a commit is reported as a finding.
- The count of open items to be walked, announced before the first subagent, is its cost bound — a target narrows the count with the walk.
- **A target selects within the `Now` order, never outside it.** A name that matches no `Now` entry stops the run before anything is spent, saying which of three it hit: nothing in `Now` is named that · it is an entry further down the roadmap (promote it first) · it is a backlog item no `Now` entry covers. It never falls back to walking the whole horizon — a mistyped name that buys one subagent per open item is the bill the target exists to avoid. Working ahead of `Now` is a roadmap change, not an argument. <!-- mis à jour 2026-08-22 : cible et refus (D-advance-target-selects-within-now) -->
- **A relayed option is recorded against its item and the walk continues.** When the chosen option is one only the user may invoke, nothing is spawned and nothing is changed: the item is recorded as gated with the option relayed, its backlog row is left exactly as it stands, the command is printed once, and the next item is walked. The row it would have closed stays open until the user runs it (see *Décisions relayées*). <!-- ajouté 2026-09-13 -->
- **A decision whose change fails its verification never lets the walk move on over it.** The change is left uncommitted in the tree, and the walk continues only if the tree is clean — otherwise the leftover edits are the dirty-tree halt, so the next item is never built on top of them. <!-- ajouté 2026-09-17 (D-failed-verification-commits-nothing) -->
- A scoped run that clears its entry says only that entry is clear, and carries the target into what it tells the user to run next.
- Same measured-elapsed rule as `/esq:autopilot`. <!-- ajouté 2026-09-09 -->
- Same model contract as `/esq:autopilot`, including the agent that applies a decision and the roadmap refresh, and the same harness-evidence refusal before the first subagent.

### Décisions relayées — les options que seul l'utilisateur peut lancer
<!-- ajouté 2026-09-13 : une option choisie est classée avant qu'un agent soit acheté pour elle (D-executability-is-read-from-the-skill, D-a-relayed-decision-is-selected-until-state-confirms-it) -->
**Résumé:** Avant de poser une décision, les trois commandes non surveillées déterminent quelles options un sous-agent a le droit d'exécuter — et relaient les autres à l'utilisateur au lieu d'acheter un agent qui ne pourrait que refuser.
**Utilisateurs:** The developer answering a 🔴 during an unattended run.
**Fonctionnement:** Two thirds of the commands are reserved for direct invocation by a person; the commonest action a decision proposes — closing a backlog row — is one of them. So every option's command is classified *before* the question is put, and an option only the user may invoke says so in its own description. Answering it costs nothing extra: the command is printed exactly as written and the run stops or walks on, according to which command is running. What the user runs afterwards is theirs; the run never reaches the same result by another road.
**Règles métier:**
- **Which actions are reserved is read from the product itself, never from a list.** The answer comes from the command being proposed, so it is right the day a command changes and cannot fall out of date.
- **An option whose command cannot be read with certainty is never handed off as a command.** A string the classification cannot place — an unknown command, several commands at once, a present step mixed with later follow-up — is quoted back as the user's answer, never printed as something to run, never cut down to a command it mentions, never made the next step. <!-- modifié 2026-09-17 : « arrête le run et la cite » → la cite, puis propose une réparation à confirmer (D-unclassifiable-do-is-quoted-never-handed-off) -->
- **esq repairs that action with the user's approval, and never picks a different one.** It reads only what the chosen option names and proposes the same choice restated as one runnable action: what it keeps, what runs now, what is deferred, how it will be checked, and what it does not do. The user approves it or pauses. When the option does not say what outcome it wants, or names nothing to check it against, esq asks for exactly that first. A step only the user may run stays that command and is relayed, never respelled so an agent can reach it. The approved repair is routed once, like any option; one that still cannot run, or fails its check, ends the attempt, and a new one is proposed only on a later run the user starts.
- **`/esq:converge` keeps the story of that answer in the brief, and resumes from its last line.** Selected · repair approved · paused · repair failed are appended, never edited, so a pause after an approval runs nothing until a new repair is approved, and a repair that failed is never tried again.
- **A change that fails its verification commits nothing and discards nothing.** Whatever the approved action, its commit — and in `/esq:converge` the strike of its 🔴 — happens only once the check the item names passes. Otherwise the edits stay in the tree for the user to see, nothing is reset or cleaned, and the run stops rather than moving on over them.
- **A relayed decision is *selected*, not applied — and it is never asked twice.** `/esq:converge` writes the chosen option and its literal command into the corrective brief, commits that alone, and leaves the 🔴 standing: answered is not done, and striking the red before the change exists makes the brief lie to the next reader. On the next run that line is the answer, not the question.
- **The itinerary only moves when the tree shows the action happened.** Resuming is decided from the ledger, never from a claim: the effect is there → the 🔴 is struck and the run resumes at the step *after* the one that gated, no work re-run; not there → the command is printed again and the run stops; impossible to tell → the run says so and hands off, erasing nothing.
- **A relayed gate makes the run cheaper, not dearer.** It adds no agent to the announced worst case, because the one it would have bought could not have run the command. A repaired one adds an agent only when its approved action is one a subagent may run.
- **Each command relays in its own way.** `/esq:converge` records the selection and stops · `/esq:advance` records it against the item and walks on to the next · `/esq:autopilot` stops and hands back to `/esq:build`.
**Décisions liées:** `D-executability-is-read-from-the-skill`, `D-a-relayed-decision-is-selected-until-state-confirms-it`, `D-unclassifiable-do-is-quoted-never-handed-off`, `D-a-repair-is-routed-as-the-action-taken`, `D-failed-verification-commits-nothing`

### Le seuil d'une question — toute commande
<!-- ajouté 2026-09-19 (D-a-question-needs-a-missing-authority, D-a-decision-authorizes-by-its-basis, D-every-orchestrator-relays-a-diagnosis) -->
**Résumé:** Ce qui vaut une interruption de l'utilisateur, et ce qui n'en vaut pas — une règle unique, la même pour toutes les commandes qui posent une question ou écrivent un 🔴.
**Utilisateurs:** The developer, as the person being interrupted.
**Fonctionnement:** Avant de demander quoi que ce soit, une commande cherche la réponse dans le mandat, le code, le plan approuvé et les décisions actives. Elle ne demande que s'il manque une autorité précise — une préférence ou une autorisation que personne n'a enregistrée — et que cette absence changerait le résultat produit, le périmètre, un engagement d'architecture majeur, une contrainte annoncée, ou un coût ou un risque que personne n'a approuvé. La demande dit laquelle de ces choses manque.
**Règles métier:**
- **Le seuil est une autorité manquante, pas un sujet.** Plusieurs options viables, de l'incertitude, ou le simple fait que le sujet soit l'UX ou l'architecture ne suffisent pas : cela se tranche et se consigne. Auparavant le tri se faisait par thème, si bien qu'un choix technique explicitement délégué revenait quand même à l'utilisateur dès qu'il touchait à l'un de ces deux mots.
- **Une panne n'est pas un choix.** Un échec, un contrôle rouge ou une preuve manquante se rendent comme un **diagnostic** — ce qui a échoué, pourquoi, et l'action exacte qui suit — jamais comme un menu d'options entre causes possibles. Les trois commandes non surveillées relaient tel quel le diagnostic de leur agent au lieu de l'habiller en décision, et n'inventent ni option ni préférence à la place de celui qui a vu la panne.
- **Le seuil s'applique là où la question naît, pas au moment de la relayer.** Filtrer à la sortie laisserait les runs surveillés poser la question quand même, et ferait juger à un orchestrateur un diagnostic qu'il n'a pas posé.

### Backlog — `/esq:backlog`
**Résumé:** The single capture bin for bugs, improvements, todos, ideas and deferred work — `docs/BACKLOG.md`.
**Utilisateurs:** The developer (manual capture and triage); every cycle command proposes into it.
**Fonctionnement:** Four modes chosen from the argument: **add** (`/esq:backlog bug: …`, captures and returns the row, never asks), **list & triage** (bare — grouped Needs-decision → Open → recently closed, one suggested next move), **update** (`B-7 done`, `pri:hi`, `type:bug`, `version v0.0.87`, `summary: …`, `note: …`, `epic:<slug>`; several IDs or a range in one commit), **publish** (one-way mirror to `docs/BACKLOG.csv` and, when connected, a Google Sheet).
**Règles métier:**
- Each row is `ID · Date · Type · Pri · Summary · Source · Epic · Version · Status`; `Status` holds exactly `Open`, `Needs-decision`, `Planned`, `Done`, `Dropped`. ID and capture date are immutable; closed items are kept as history, never deleted.
- A manual add always gets a priority; one the user did not set carries a `?` (`med?`) as a suggestion. Items proposed by build/check/review land unprioritized.
- Structured fields live in the table row only; detail sections hold prose (`What` · `Why it matters` · `Notes` · `Resolution`).
- A batch naming a non-existent ID aborts before anything is written (a range just skips holes); per-item changes refuse the batch form.
- Past 1 500 lines, triage prunes the detail of `Done`/`Dropped` items (row kept, `git show` pointer added). Open work is never pruned; quick-add never prunes.
- **The command holding the evidence writes the disposition.** Build, check, review, fix and work file their own observations, each row carrying where it came from; build and fix close a row only when its whole promised outcome was delivered and verified, recording what delivered it in the same write. A row a command closed that was not delivered is worse than one left open, so partial delivery stays open, and no row is ever dropped, re-filed or re-classified to get past a gate. Accepting a defect unfixed stays the user's call. <!-- modifié 2026-09-11 : « build, check, review et fix proposent les clôtures ; aucun n'en écrit » → ils déposent et ferment eux-mêmes ce que leurs preuves établissent (D-evidence-settles-backlog-dispositions) -->
- **Every working copy numbers from its own ID block.** The main checkout keeps `B-001…999`; a parallel worktree — however it was created — reserves its own block on its first new row, and two worktrees reserving at the same moment always get different blocks. No number is ever minted from someone else's range. <!-- ajouté 2026-09-11 (D-a-linked-worktree-reserves-its-block-under-one-lock) -->
- `Version` filled means deployed / ready for acceptance; `Done` means acceptance passed.

### Ledger reconciliation — `/esq:sweep`
**Résumé:** After a batch of work, closes the backlog items the evidence settles and asks only about the rest.
**Utilisateurs:** The developer, after shipping a lot.
**Fonctionnement:** Picks a window (since the last sweep, a release tag, an explicit range, or `dry` to report only) and splits every open item three ways: **settled** (plan fully completed, a commit names the ID, a green `/esq:fix` applied, or a checkable state already holds) → closed and committed without asking; **ambiguous** (evidence plus a judgment) → one numbered question, answered `1,3` / `all` / `none`; **untouched** → not listed. Stamps `<!-- last-sweep: … -->` in the backlog header even when it closed nothing.
**Règles métier:**
- A doubtful item goes to ambiguous, never to settled.
- `/esq:sweep v0.0.87` stamps that release into the `Version` column.
- Status synonyms (`Resolved` → `Done`) are rewritten; unknown values are asked about; both are reported under `Ledger defects`.

**Résumé:** `docs/DECISIONS.md`, the log of architectural, product, functional and UX decisions.

### Product spec — `/esq:spec`
**Résumé:** This document: a PO-level, feature-by-feature account of what the product does.
**Utilisateurs:** Product owners; read by grill, plan, check, review, arch and status.
**Fonctionnement:** First run mines the codebase and writes `docs/SPEC.md`; later runs refresh it, adding new features and updating prose freely.
**Règles métier:**
- **A documented business rule the code no longer honors is never absorbed silently.** The user is asked "intended?" — yes → the rule is rewritten with a dated note; no → the spec is left untouched and the regression is reported. Vanished features are marked `Retiré`, not deleted.
- Staleness is computed from the `<!-- last-spec: … -->` marker against user-facing phases shipped since; nothing ever auto-runs the refresh.
- **The marker also records the commit the spec was mined from**, which is what lets `/esq:land` report whether the spec still describes the tree: code, the decisions registry or a project skill changing since makes it stale, while bookkeeping — the spec itself, the architecture documents, plans and the backlog — does not. A marker carrying only a date proves nothing. <!-- ajouté 2026-09-11 (D-projections-carry-their-mining-commit) -->

### Architecture projection — `/esq:arch`
**Résumé:** Re-reads the codebase and maintains how it is built: a thin `CLAUDE.md`, topic skills, and a deep `docs/ARCHITECTURE.md`.
**Utilisateurs:** The developer of a consuming project; every future session reads the output.
<!-- mis à jour 2026-09-11 : `CLAUDE.md` garde les règles dont l'oubli est silencieux ou coûteux, pas « bruyant » ; le marqueur porte le commit miné -->
**Fonctionnement:** Routes every rule by what a miss costs: always-loaded `CLAUDE.md` (under an 80-line gate) for the rules whose miss is silent or expensive, `.claude/skills/` for topic rules whose miss is loud and runnable recipes a session would otherwise re-derive, `docs/ARCHITECTURE.md` for boundaries, flows, patterns and why. Reports spec staleness and adds a pointer to the spec in the docs map.
**Règles métier:**
- Never writes the spec.
- Evicts from `CLAUDE.md` rather than letting it grow.
- **Its marker records the commit it mined, so `/esq:land` can report whether the architecture documents still describe the tree.** When a refresh rewrites project skills it commits them first and records that commit, so its own refresh never stales it — and because a skill change stales a spec mined before it, `/esq:spec` then runs after `/esq:arch`. <!-- ajouté 2026-09-11 (D-projections-carry-their-mining-commit) -->
- **A runnable skill owns the environment its recipe needs.** Setup must be idempotent, leave nothing for the caller to undo, and require nothing the script cannot compute about itself — an install the caller reverts every session, or an invocation the caller hand-assembles, moves the re-derivation rather than removing it, and moves it somewhere no automated check will ever go red. <!-- mis à jour 2026-08-21 : clause d'environnement dans le test de re-dérivation (B-069) -->

### UI/UX audit — `/esq:ui`
**Résumé:** Audits the interface as actually built and hands back a direction to pick.
**Utilisateurs:** The developer of an app with screens.
**Fonctionnement:** Reads the screens in the code, drives the running app and looks at it, checks current practice outside the repo, renders two directions on the busiest screen on a published comparison page, asks the user to pick one, and writes a brief for `/esq:plan`.
**Règles métier:**
- Announces the screen list before spending anything, so the user can redirect it for free.
- **Un mode greenfield rend deux directions pour un produit sans interface.** `/esq:ui --greenfield` n'audite rien : il n'y a pas d'app. Le mode ne s'active que par le drapeau, jamais par déduction — un lancement qui échoue demande l'accès, il ne bascule pas ici. <!-- ajouté 2026-09-20 (D-greenfield-is-a-ui-mode) -->
- **Greenfield rend du vrai contenu ou ne rend rien.** La source est résolue dans cet ordre : le brief d'interrogation nommé, `docs/SPEC.md`, puis la copie collée dans l'invocation. Une *description* de l'écran n'est pas de la copie et ne compte pour aucune des trois. Si aucune ne répond, la commande s'arrête avant de rendre quoi que ce soit et dit ce qu'il lui faut. Chaque mot affiché trace jusqu'à la source ; ce que la source ne nomme pas est rendu comme un placeholder visible (`[titre]`, `[3 lignes de données]`), jamais comme de la copie inventée. <!-- ajouté 2026-09-20 (D-greenfield-keeps-pasted-copy-as-a-source) -->
- **Cinq points nommés barrent chaque direction avant qu'elle soit montrée**, et une direction qui en rate un est corrigée puis re-vérifiée, jamais publiée avec le défaut annoté : contraste AA du texte courant calculé depuis ses propres tokens, un état de focus visible sur chaque élément interactif, des cibles tactiles d'au moins 44 × 44 px, aucun défilement horizontal à ~400 px de large, et les états vide / chargement / erreur réellement rendus. Les trois points du milieu se lisent en valeurs mesurées dans la session du navigateur, pas sur une capture. <!-- ajouté 2026-09-20 (D-greenfield-gate-reads-values-not-looks) -->
- **La page publiée porte la preuve ou porte l'absence, jamais rien.** Quatre emplacements — 2 directions × 2 thèmes, les deux thèmes étant inconditionnels — et chacun montre soit la capture, soit la ligne « non rendu — pas de pilote de navigateur ». La dépense reste au plus 4 captures : la part du passage live, supprimé, est réallouée à la lecture extérieure, et le plafond annoncé ne monte pas. Le brief répète le même verdict, et porte une ligne explicite disant qu'aucune lecture live n'a eu lieu. <!-- ajouté 2026-09-20 -->
- **Un seul brief par tâche.** Quand la source était un brief d'interrogation, il est enrichi sur place — jamais un second brief sur le disque pour le même travail. <!-- ajouté 2026-09-20 -->

### Orientation — `/esq:status`

**Résumé:** Read-only snapshot: where the project is and the one next action.
**Utilisateurs:** The developer at the start of a session.
**Fonctionnement:** Reports the active plan and current phase (including a phase attempted but never logged, detected from commits the log does not account for), pending briefs, backlog counts, head of the roadmap, the active plan's epic rollup, arch and spec staleness, the freshness of the harness measurements, and `→ Next`. When a plan file or the backlog table is unreadable, it still renders every healthy fact: each unreadable file is named in the "needs you" zone with its fault and the remedy (`esq validate` for the full list, fix by hand), the current phase is read off the newest healthy plan, the backlog line carries the fault instead of counts (never a zero), and `→ Next` is computed over the healthy plans only.
**Règles métier:**
- Lists items still `Planned` on a plan whose every phase completed — the passive net under the cycle's close proposals.
- **A stale harness measurement is stated, never turned into a next action.** Re-measuring costs real money, so the report names the claim, the two version numbers and the exact command that would refresh it, and stops there — the decision to spend is the user's. A measurement nobody has taken yet, or one whose verdict could not be computed, is a fact and not a warning; only a genuinely stale one colours the line.
- **A completed plan is routed to what it still needs, never back through a loop it already closed.** Landed → nothing is recommended for it; a corrective brief still carrying items → `/esq:fix` (a 🟢 remains) or `/esq:plan`; no clean review ever recorded → `/esq:check`, or `/esq:converge` to run the loop unattended; a recorded review that code changed since → `/esq:review`, never the whole loop again; an open defect the unit filed against itself → `/esq:work` on it, with accepting it unfixed offered as the user's alternative; a promised row still undisposed → mark it done if it was delivered, otherwise plan it; otherwise → `/esq:land`. <!-- modifié 2026-09-11 : « une ligne backlog non disposée → /esq:backlog » → un défaut non corrigé va à /esq:work, jamais vers « done » ; une promesse est done si livrée, sinon planifiée --> A legacy plan with no recorded origin is recommended nothing. <!-- mis à jour 2026-09-11 (D-a-unit-lands-when-every-plan-is-built-or-abandoned, D-projection-freshness-is-advice-at-landing) --> Before any of that, a complete plan whose branch still carries an unbuilt or paused sibling plan is routed to `/esq:build` on that sibling, with recording it abandoned offered as the user's alternative — never to `/esq:land`. - Reports, never diagnoses or writes.
- A broken ledger is a `⚠` headline with the file named, never a blank report and never a silent fallback to re-reading every file by hand.

### Parallel sessions — `/esq:worktree`
**Résumé:** Runs two esq sessions on one codebase safely, with a reserved backlog ID block each, and merges them back.
**Utilisateurs:** The developer who wants two sessions at once.
**Fonctionnement:** `<name>` creates a branch and a sibling worktree, reserves a backlog ID block (`B-1000…1999` for the first, `B-2000…` for the next; main keeps `B-001…999`) and hands back the one line to paste into a new terminal. `ls` lists; `merge <name> [into <dest>]` merges the branch and reconciles the backlog and decisions ledgers; `rm <name>` removes the worktree and offers to delete a merged branch. A shell script offers the same create/ls/rm outside Claude, reserving through the same allocator. <!-- mis à jour 2026-09-11 : un seul allocateur, sous verrou -->
**Règles métier:**
- **Two worktrees created at the same moment never share a block.** Choosing the block and recording it happen as one step that every worktree of the repository waits its turn for. If a crashed process left that turn held, the next reservation refuses after ten seconds and names what to remove, rather than guessing it is safe to take over. <!-- ajouté 2026-09-11 (D-a-linked-worktree-reserves-its-block-under-one-lock) -->
- **No block is ever chosen by hand.** When the allocator cannot run — no Node, or the plugin's command-line tool absent — the shell script refuses before creating anything, and the attended command keeps the worktree but reports it has no block yet, naming the one command that reserves it. <!-- ajouté 2026-09-11 -->
- **An ID is never changed to resolve a collision.** If one ID was minted independently on both sides (absent at the merge base), the merge aborts, names both entries and how many places cite the ID, and hands the call to the user.
- An ID that existed at the merge base is one item both sides edited: reconciled cell by cell into one row — a cell only one side changed takes that side; `Status` takes the further-along value, `Pri` the higher, blank loses to non-blank; two different free texts, a `Dropped` against another status, or a conflicted detail section are asked about once.
- Merge touches only the ledgers; `CLAUDE.md`, `ARCHITECTURE.md` and `SPEC.md` conflicts are left as git left them and reported, the merge held uncommitted, never thrown away.
- The only manual step is opening the second terminal.
**Décisions liées:** `D-004`, `D-merge-base-decides-shared-row`, `D-derive-else-ask-on-cell-conflict`, `D-boundary-anchored-ledger-id-match`

### Branch ownership — `**Branch:**`, `esq branch check`
<!-- mis à jour 2026-09-10 : le verdict porte aussi les défauts ouverts de l'unité, et une souche reprise par cherry-pick est lue comme atterrie -->
<!-- ajouté 2026-09-01 : le plan enregistre sa branche et `/esq:build` refuse une branche qu'il ne possède pas (B-102) -->
**Résumé:** A plan records the branch its phases commit to, and a build refuses to run anywhere else — so a range of commits always maps back to exactly one plan.
**Utilisateurs:** Any developer running plans, and especially anyone running several in parallel worktrees.
**Fonctionnement:** `/esq:plan` writes two header fields: `**Origin:**`, the branch it was invoked on, and `**Branch:**`, the `esq/<slug>` branch it cuts from that origin and commits the plan file to. The pair is the shipping unit — where the phases commit, and where the work lands. Before `/esq:build` reads a phase — before it opens the plan file at all — it asks `esq branch check` for one verdict, and on a refusal it stops and hands back a lettered option set rather than moving anything. `esq branch check <plan>` is runnable on its own; it reads git, the plan files and the backlog, writes nothing, and is the only thing that decides ownership. The same verdict also reports the shipping unit: which plans belong to it, and which of its own bug and debt rows nobody has disposed of. <!-- mis à jour 2026-09-10 --> For a landing it adds four facts, each read from the ledgers and git and none judged: the backlog rows the unit's plans promised and nobody has closed, the unit's corrective briefs still carrying items, whether the unit has already landed on its origin, and whether a clean review still covers the tree. <!-- mis à jour 2026-09-11 (D-a-landing-reads-coverage-and-obligations) --> <!-- modifié 2026-09-04 : le plan taille sa propre branche et enregistre l'origine (B-116) -->
**Règles métier:**
- **Five verdicts, three of which refuse.** `ok` (the recorded branch, claimed by no other shipping unit) and `unrecorded` proceed; `mismatch` (HEAD is on a different branch than the plan records), `detached` (a phase committed to a detached HEAD could never be attributed later) and `owned-elsewhere` refuse. <!-- modifié 2026-09-04 : `trunk` supprimé -->
- **Ownership is a claim between shipping units, and `**Origin:**` is the marker.** A plan recording no origin is legacy: it owns no branch, is owed none, and never lands — which is what keeps every plan written before the field existed building. The repository's default branch is not an input to the verdict at all. <!-- modifié 2026-09-04 : « la branche par défaut ne possède rien » → l'unité d'expédition est le marqueur -->
- **Ownership alone refuses, merged or not.** A branch already recorded by a different plan is refused whatever its merge state — ancestry is not identity, so whether the other work landed is reported as a fact in the message and never decides. A plan and its corrective `-fixes` sibling share a stem, are one shipping unit, and legitimately share a branch.
- **Absence authorizes nothing.** A plan with no `**Branch:**` field is `unrecorded` and refuses nothing; that is what lets every plan written before the field existed keep building.
- **A worktree only sees its own plans.** Ownership is computed from `docs/plans/` in the current working tree, so two linked worktrees can each record the same branch name without either verdict noticing — git's own refusal to check one branch out twice is what prevents the collision. The verdict says what it can see and claims no repository-wide knowledge.
- **The shipping unit is every plan recording the same branch, and it is asked what it filed against itself.** A plan and its corrective siblings share one branch, so they are one unit however many rounds deep the chain runs. The unit's open defects are the bug and debt backlog rows whose source names one of its `build:` or `fix:` steps and whose status is neither Done nor Dropped — three table cells and one header field, no judgment of severity and no inspection of which file the defect is in. `/esq:build` refuses to log a phase complete while one stands, and `/esq:converge` refuses before its first subagent. <!-- ajouté 2026-09-10 -->
- **A stem whose commits reached its origin by cherry-pick or rebase has landed.** When a corrective plan asks which branch it belongs on, "has the stem landed?" is answered by ancestry first and by patch equivalence second, so a stem that was cherry-picked or rebased onto its origin is no longer read as still in flight and the correction is cut its own branch instead of being committed where nothing will merge it. A squash-merged stem is equivalent to none of its own commits and still reads as in flight — a known residue, and it fails in the safe direction, since a needless fresh branch costs a name where a wrong reuse costs the commits. <!-- ajouté 2026-09-10 -->
- **The refusal is a decision handed back, never taken — and what is handed back runs.** `/esq:build` and `/esq:converge` never run a `git switch` and never edit the `**Branch:**` field to let themselves proceed — that field belongs to `/esq:plan` alone *among commands*, and rewriting it there would turn the guard into a rubber stamp. The rule binds commands, never the human: the escape the option set offers is the user's own edit of their own plan header, and option A names it as a second step — `git switch -c esq/<slug>`, then, unless the header already names that branch, edit `**Branch:**` to it and re-run. Neither half clears the gate alone, so an option set that offers only the switch offers a `do:` that leads back to a refusal. <!-- modifié 2026-09-05 : la propriété d'écriture unique lie les commandes, pas l'utilisateur ; l'option A porte deux étapes (B-120) -->
**Décisions liées:** `D-a-plan-owns-its-branch-trunk-owns-nothing`, `D-a-shipping-unit-lands-where-it-started`, `D-a-cherry-picked-stem-has-landed`, `D-the-unit-is-keyed-on-branch`

### Cost and reporting contract — every command
**Résumé:** Every command tells the user what it will spend before spending it, asks only what the repo cannot answer, and concludes in one fixed shape.
**Utilisateurs:** Everyone running any `/esq:*` command.
<!-- modifié 2026-09-11 : annonce en paragraphe, « besoin de vous » pouvant porter des notes → une ligne d'annonce suivie de l'action dans la même réponse ; seules les demandes encore ouvertes, chacune exécutable ; → Next répète la première (D-announcements-and-asks-stay-minimal) -->
**Fonctionnement:** A command that can run for minutes opens with one line stating its bound, before its first tool call — and keeps going in the same response rather than ending on that line — then a second line naming the resolved target once known; it ends with elapsed time. Reports use three zones: a one-line headline (`✔`/`⚠`/`✖`, counters, elapsed, `NEEDS YOU (n)`), what needs the user — only requests they still have to settle, never a notice and never work the command could have done itself, each executable one carrying its exact command — and one line per fact. Then `→ Next`, alone: the first pending request's command repeated, so the last line on screen is what to run. Unattended commands also send a push notification at the end and before any gate.
**Règles métier:**
- A stop is earned only by intent, a tradeoff hinging on the user's constraints, genuine scope ambiguity, or a screen only a human can judge — never by permission to write a revertible file, confirmation of a proven-safe operation, or a question the outside world already settled.
- No command ever runs another esq command automatically; orchestrators dissolve `[context]` stops only, on a fixed itinerary with a stated bound.
- Four commands that hand back within a minute (`status`, `backlog`, `epic`, `worktree`) are exempt from the announcement by name.
- **A decision's action settles that decision now, and nothing later.** Follow-up work a choice defers — a refresh after shipping, a step once something lands — is written into the option's consequence, never into the command the user copies, because whatever answers the question runs that command at once. Keeping things as they are is still an action: it checks the state being kept and records the acceptance against that one decision. <!-- ajouté 2026-09-17 (D-unclassifiable-do-is-quoted-never-handed-off) -->
- **An announcement never ends the turn.** Its bound is real — no estimated duration — and the work starts in the same response. A few runs used to stop right after saying they would announce, and the user had to re-send the command; a check now fails the build if the wording that invited that stop returns, though only later sessions can show the stop itself is gone. <!-- ajouté 2026-09-11 (D-announcements-and-asks-stay-minimal) -->
- **Every ask is one line, and it opens with the action.** What the user is being asked to do comes first — an imperative verb, roughly a dozen words, one sentence — with no lead-in above it and no restatement under it: a decision's headline is the verb-first 🔴 with its options directly beneath and nothing in between, and a manual verification carries its starting state in brackets at the front of the same line rather than on a line of its own. A reader scanning `NEEDS YOU` sees what to do, not a paragraph describing the situation. <!-- mis à jour 2026-08-22 : forme de la demande, action en tête (D-ask-shape-lives-in-zone-two) -->
- Model choice defaults to the most capable model; a cheaper one is pinned only where the task is confirmed mechanical, and five commands are that case. The three unattended orchestrators are **not** pinned at all: they relay rather than judge, so they take the model of the session they were invoked from, while still launching every worker on the capable model explicitly and checking it was served. Making an unattended run cheap is therefore something the user types (`/model sonnet`, or `--model sonnet` on a headless call) rather than something the product decides — and that saving holds only while the harness-routing measurement is fresh: under a stale one, a non-Opus session is refused before the first spawn, so an unattended run either stays on the capable model or keeps the measurement current. <!-- modifié 2026-08-19 : « un modèle moins cher seulement là où la tâche est mécanique » → les trois orchestrateurs sont ce cas, avec modèle des workers choisi explicitement et vérifié (D-relay-sonnet-workers-explicit-opus) --> <!-- modifié 2026-09-03 : « les orchestrateurs tournent bon marché » → ils ne sont plus épinglés et prennent le modèle de la session ; l'économie est tapée par l'utilisateur et conditionnée à la fraîcheur de la mesure (D-relay-inherits-the-session-model) -->
- **A file already read this run is not read again.** The five commands that do the work (`build`, `check`, `review`, `fix`, `work`) carry the rule outright: what was read is quoted back from context rather than re-fetched, a large file is sliced in one pass rather than reopened, and the only exception is a file the run itself wrote since. Measured over 158 runs, re-reading a path the same run had already read cost 757 round trips — 4.8 per run, 16.5% of every tool-issuing turn, `docs/BACKLOG.md` alone 71 times. <!-- mis à jour 2026-08-21 : règle read-once dans les cinq commandes de travail -->
- **What is independent is issued together; what is ordered is chained.** Six commands (`build`, `check`, `review`, `fix`, `work`, `plan`) carry the rule: read-only calls with no shared mutable state — file reads, greps, `git log`/`show`/`status`, an `esq` read verb — go out as parallel calls in one turn, while anything ordered or touching shared state is chained in a single call, in order, so a failure stops the chain. **Git mutations are never issued side by side**: `add`, `commit`, `switch`, `rm`, `mv` and `merge` all contend for the index, `HEAD` and the working tree, and the same holds for two writes to one file or a read of a file another call in the same batch writes. Three shapes recur — a command's opening preflight reads, independent verification commands that do not feed each other, and the git transactions a command's tail owes. Measured 2026-08-21 over 621 subagent transcripts, esq's own agents issued 1.068 tool calls per turn against 1.243 for the 446 non-esq agents on the same machine; closing that gap is about 4 round trips per run. Batching is about how calls are *issued* and is never a reason to merge two implementation commits, which stay one per task. <!-- ajouté 2026-09-08 : règle batch-independent dans six commandes -->
- **A command's own bookkeeping costs one commit, not two.** Where a command owns every file in its tail at that moment, those writes land together: `/esq:check` and `/esq:review` commit the fixes brief with the backlog rows they escalate, `/esq:fix` commits the rewritten brief with its escalation row, `/esq:plan` commits the plan file with the decisions, the backlog status flip it caused and the corrective brief it retired, and `/esq:work` commits the plan anchor with the backlog close. Implementation commits are never merged into these — reverting a plan should revert the status flip it caused, but reverting a fix should revert only that fix. <!-- ajouté 2026-09-08 : consolidation des queues de comptabilité -->
- **What each command costs is published as a measurement, not a claim** — a dated table of runs, median tokens, median duration and median tool calls per command, read off the telemetry the plugin collected, with subagent runs and typed-in-session runs kept apart because the second includes the user's own waits. No monetary figure is ever shown: the product holds no per-model price. <!-- mis à jour 2026-08-20 : tables de coût mesuré (B-029) -->
- **A published pin moves only on evidence of outcome, never on spend alone.** The first measurement confirmed no command on more than one model, so every pin held and the table states, per command, why: measured one run short on a second model, measured on one model only, or held structurally and unmeasured. A tier changes only when a second model reaches the sample threshold *and* a signal exists for whether the work was any good. <!-- mis à jour 2026-08-20 : D-tiers-held-until-a-second-cell-confirms -->
- **Each confirmed command group carries a regression budget** — half again its measured median output tokens and duration, carrying the sample size and the date it was set from — and a check compares today's telemetry against it, one line per group. A breach is an investigation, not a failure: it says a command now costs more than it did on that date, which may be a regression or a fair price for work it did not do before. A group that falls back below the threshold is reported as not compared, never as fine. <!-- mis à jour 2026-08-20 : budgets de régression (B-029) -->
**Décisions liées:** `D-announce-in-two-beats`, `D-long-run-is-an-opt-out-list`, `D-elapsed-footer-over-conclusion-block`, `D-opus-default-sonnet-only-mechanical`, `D-relay-inherits-the-session-model`, `D-tiers-held-until-a-second-cell-confirms`, `D-cost-budget-checked-outside-the-audit`, `D-budget-is-one-and-a-half-times-the-median`, `D-ask-shape-lives-in-zone-two`, `D-announcements-and-asks-stay-minimal`, `D-unclassifiable-do-is-quoted-never-handed-off`

### Fraîcheur des mesures du harnais — `docs/EVIDENCE.md`, `esq evidence`
<!-- mis à jour 2026-09-03 : toute mesure au-delà de « jamais mesurée » nomme une capture dont la version doit égaler celle de sa ligne ; le protocole manuel écrit lui-même sa capture, ses deux directions sur une seule version de Claude Code ; un protocole documenté est vérifié en exécutant sa sortie -->
**Résumé:** Records which claims about Claude Code's behavior rest on a real measurement, on which version it was taken, and whether that version is still the one installed.
**Utilisateurs:** The developer deciding whether a claim can still be trusted — and the unattended commands, which refuse to spawn on one that cannot.
**Fonctionnement:** A registry lists one row per measurement: what it is evidence of, the recorded results, the version of Claude Code they were taken on, the date, and the exact command — a billed harness run, or a written one-session protocol — that would take a fresh one. `esq evidence` reads it against the installed version and answers, per claim, *fresh*, *stale*, *never measured* or *unknown*. `/esq:status` shows the answer beside the other staleness lines; the three unattended commands read it once before their first subagent. Nothing in it is computed or refreshed automatically — a new measurement is a run someone pays for, and appending its row is what activates it.
**Règles métier:**
- **The registry only grows.** A measurement is never renumbered, repointed, edited or deleted — it is the permanent record of one run on one day. A new one is a new row, and the only edit ever made to an old one is marking it superseded.
- A claim's current measurement is the one row explicitly marked as current — never the newest date, never the last line. None, or two, reads as *unknown*.
- **A measurement that was run but never registered refreshes nothing.** The claim stays exactly as stale as it was, and the orphan result file is named in the report so the omission is visible rather than silent.
- **Only one claim gates anything today** — whether an explicitly requested model is actually honored — and it gates exactly one thing: an unattended command's first spawn. Every other claim is informational in every state, including never measured, and blocks nothing.
- Unknown is treated as stale. Evidence nobody can read is not evidence.
- **Every measured row names a capture, and the capture states its own version.** Any row past *never measured* names a committed artifact holding the records the reading came from, and the version those records state for themselves must equal the row's version cell. The floor is the same whether a billed harness wrote the capture or a maintainer did by hand — a measurement whose evidence nobody outside the room can open is not one.
- A never-measured claim is reported as a gap, not a regression: one claim (does a model pin bite in a live typed session?) has no automated way to be measured at all and carries a written one-session protocol instead. That protocol's last act is writing its own capture, and its two readings must be taken on a single Claude Code version — a version that moved between them makes it two measurements, and the registry refuses the pair.
- **The placeholder for a never-measured claim is never retired.** Taking the measurement appends a new row; the placeholder stays where it is, so no step of any protocol asks anyone to delete or edit a registered row.
- **A documented protocol is verified by running its output, not by reading its prose.** The build materializes the row the protocol tells a maintainer to write and fails if the registry reader would refuse it — a procedure that produces an illegal registry reds the build instead of surfacing the next time someone follows it.
- **Evidence already paid for survives the interrupt.** A billed measurement spends real money per row, and each row's records are on disk before the next row is bought — so pressing Ctrl-C, closing the terminal or losing the session keeps every row that had already completed, at a path the run printed *before* it spent anything. - Completion, pause, failure and gate notifications stay in the skills, which know the outcome; no generic hook infers them.

### Installation and release
<!-- mis à jour 2026-09-07 : la mise en service d'une version vérifiée est une commande, et l'absence de version est un échec de build (B-097) -->
<!-- mis à jour 2026-09-10 : la publication ne revalide plus le produit ; elle prouve d'abord que rien d'autre n'a bougé (D-the-publisher-revalidates-nothing, D-plugin-management-runs-bare) -->
<!-- mis à jour 2026-09-10 (bis) : l'appel d'installation ferme aussi son entrée standard ; le produit ne dépend plus de la façon dont la commande a été lancée (D-plugin-management-closes-stdin) -->
<!-- mis à jour 2026-09-11 : la vérification que la publication ne refait pas appartient à `/esq:land` (D-update-publishes-land-verifies) -->
**Résumé:** The product installs as a Claude Code plugin and is put into service on a machine by one release command that proves what it installed. <!-- modifié 2026-09-22 : l'installateur par commande et son repli sont retirés ; le plugin est la seule voie -->
**Utilisateurs:** The developer installing esquisse; its maintainer, once verified work has landed.
**Fonctionnement:** The plugin is the primary install (marketplace or `--plugin-dir`). Once verified work is on the main line, one command bumps the version in both manifests, proves that the version bump is the only thing in the working copy, makes a single release commit, installs through the official plugin-update path, and then proves the installed copy equals the source on version, commit and bytes — ending by saying that running sessions must be restarted to pick it up. The same command asked for a report instead answers what is installed, whether it matches the source and whether a release is owed, and changes nothing. The legacy installer deploys a command directory and prunes what the repo no longer provides.
**Règles métier:**
- **A release is demanded, not remembered.** The build fails when the shipped code has moved past the last version bump, or when the two manifests disagree on the version — the failure that let 662 commits ship under one version number.
- **A release refuses before it writes.** The wrong branch, a dirty tree, a secondary checkout, manifests already disagreeing, or nothing having changed since the last bump each stop it with the condition named and the tree exactly as it was found.
- **Once the release commit exists, it stands.** Any failure after it — the install, the proof — reports what broke and prints the retry line; it never reports success and never rewinds. A release that half-happened stays visible as a half.
- **The release publishes; it does not re-verify.** Checking that the product itself is sound belongs to `/esq:land`, before the branch lands, and re-running it here would be paying twice for the same answer. What the release proves instead, before committing, is that nothing else moved: the tree was clean when it started, both manifests parse, both carry the new number, and the only difference from what is recorded is those two version fields — no stray file, no second edit. Any of those failing puts the manifests back and refuses before a commit exists. <!-- ajouté 2026-09-10 -->
- **A successful release makes exactly one call to Claude Code — the install.** Every such call it does make asks for the plugin-management path only, without starting a full session, after a release was observed sitting for three minutes on a call that took half a second that way; the printed retry line is the same call, so what the user is told to re-run is what ran. The root cause of the stall is not claimed to be known. <!-- ajouté 2026-09-10 -->
- **That call also stops listening to the terminal it was launched from.** Asking for the plugin-management path was only half of it: the same call still waited out its full three-minute limit when it inherited the keyboard, and finished in half a second when it did not. So the product closes that input itself, on every install and every check it runs, and the retry line it prints does the same. What a maintainer gets is a release that behaves identically whether it was typed at a prompt, run from a script or run unattended — and one that no longer depends on anyone remembering a detail of how it was launched. Why the wait happened is still not claimed to be known. <!-- ajouté 2026-09-10 -->
- The report form is not a gate: it is safe from any branch at any time and never turns its answer into an exit status.
